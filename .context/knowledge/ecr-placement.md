## Capability and current implementation

ECS can pull private images from ECR in another region. The task uses the source registry's full image URI; its platform pull role needs permission on those source repositories. Regional ECR is a locality/recovery choice, not an ECS requirement. Same-account centralization needs no cross-account trust. Our public-subnet host already has outbound access; it would not require peering, a NAT gateway or new ECR private endpoints. [AWS ECR FAQ](https://aws.amazon.com/ecr/faqs/), [ECS pull permissions and image references](https://docs.aws.amazon.com/AmazonECR/latest/userguide/ECR_on_ECS.html).

Ghostline now maintains three common `ghostline/prod/` repositories per participating region in `GhostlineRelease`, independently of disposable endpoints. [Release workflow](../../docs/releases.md) owns publication, native replication, complete-set gates and bounded retention. Endpoint park/destroy preserves the durable release stack. Platform image pulls preserve the no-task-role boundary; engines need no AWS credentials.

Central-registry unavailability would affect uncached launches, updates and recovery, rather than interrupt already running VPN tunnels. ECS container definitions accept one image URI, with no primary/fallback registry list. Switching to a copy in another ECR region requires selecting that URI in a new task definition and deploying it; automatic selection would be custom orchestration. Match the intended release identities and grant the platform pull role access to the alternate repositories. [ECS container image field](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDefinition.html).

On EC2, the agent's default pull policy tries the remote image and falls back to a locally cached image if the pull fails. `always` instead fails the task; `once` and `prefer-cached` prioritize reuse under their documented conditions. Ghostline's checked-in bootstrap does not override `ECS_IMAGE_PULL_BEHAVIOR`; live host settings and registry-outage recovery were not tested in this review. Cache fallback is not cross-registry failover and cannot recover a cold host without the required images. Keep regional copies as the recommendation, with any future alternate-source selection in regional activation rather than assuming ECS discovers replicas. [ECS EC2 image pull behavior](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/pull-behavior.html).

## Regional outage proxy follow-up — September 21

Anthony clarified that the objective is surviving loss of an image-source region, not fixing a missing image registration. AWS documents regional ECR endpoints and independent copies, without an ECR equivalent of a global failover proxy. An ALB cannot directly register public ECR addresses as targets. A custom registry-aware proxy is possible in principle, but must handle client TLS/authentication, upstream regional credentials, repository routing and layer downloads, plus its own cross-region availability. DNS switching alone does not supply that behavior: ECR authorization tokens are region-specific, and image layers are served from regional S3 storage. This is an architectural assessment, not a tested proxy design. [ECR regional endpoint model](https://aws.amazon.com/blogs/containers/amazon-ecr-in-multi-account-and-multi-region-architectures/), [ALB target restrictions](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html), [regional authentication](https://docs.aws.amazon.com/AmazonECR/latest/userguide/common-errors-docker.html), [ECR/S3 pull path](https://docs.aws.amazon.com/AmazonECR/latest/userguide/vpc-endpoints.html).

The earlier review omitted a useful managed alternative: **ECR-to-ECR pull-through cache**, available since March 2025. A downstream regional ECR can import images from a source ECR in another region/account on demand. AWS explicitly serves the last cached image when an upstream refresh fails, including after the 24-hour freshness window. That protects a healthy destination from an upstream outage once the required image is cached, including launches on fresh EC2 hosts; it is independent of the host's Docker cache. It cannot supply an uncached release while the source is unavailable or make the downstream ECR region survive its own outage. [Launch announcement](https://aws.amazon.com/about-aws/whats-new/2025/03/amazon-ecr-pull-through-cache/), [cache behavior and limits](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache.html).

Recommendation remains complete release copies in each activated region, with no image-source-region API prerequisite for restart/rebuild. The selected native-replication workflow now provides those copies; the earlier deferral was superseded. Pull-through caching is another distribution candidate, not a selected change. Prewarm and verify every required artifact before declaring a region recovery-ready. The cache's 24-hour tag freshness behavior does not independently meet the proposed immediate `production` promotion workflow; retention, refresh and complete-set digest verification must be designed together. If the compute region itself is lost, use an exit in a surviving region. If only its ECR service fails while compute remains usable, cached host images or explicit alternate-registry orchestration are separate mitigations. No cloud configuration or outage test occurred.

### Custom domain indirection

A plain CNAME from a Ghostline domain to a regional ECR hostname is not a transparent Docker/ECS registry alias. TLS verifies the hostname in the requested image URL; a DNS alias does not make ECR's certificate cover our domain. AWS's supported ECS image reference contains the actual regional ECR registry hostname, and ECR authorization tokens are region-specific. A custom-domain proxy therefore needs TLS termination and registry authentication/routing, not only DNS failover. [TLS reference identity rules](https://www.rfc-editor.org/rfc/rfc9525.html#section-6.1.1), [ECS image references](https://docs.aws.amazon.com/AmazonECR/latest/userguide/ECR_on_ECS.html), [regional authentication](https://docs.aws.amazon.com/AmazonECR/latest/userguide/common-errors-docker.html).

DNS could instead be a discovery input to our publisher/deployer: read a preferred region or registry locator, validate it against expected account/regions/repositories, then authenticate and use the real ECR hostname. ECS receives that concrete image URI; changing the discovery record does not switch existing task definitions. This is a proposed tooling design, not native transparent ECS failover. Recommendation: keep native regional image pulls and put optional publication-source selection in the release tooling; a domain is optional and does not remove the need for that logic. No DNS, certificate, proxy or publisher changes were made.

### Replication versus pull-through

These are distinct distribution mechanisms: replication proactively copies matching new ECR publications to configured destinations; pull-through imports a requested image when a client pulls through the destination ECR. A first cache miss waits for the upstream import. Subsequent tagged pulls use the cached image within the 24-hour validation window and check upstream after it expires; this is pull-triggered validation, not a guaranteed daily background synchronization job. Both provide source-outage independence only for content already present in a healthy destination. [Replication](https://docs.aws.amazon.com/AmazonECR/latest/userguide/replication.html), [cache semantics](https://docs.aws.amazon.com/AmazonECR/latest/userguide/pull-through-cache.html).

Pull-through also supports public upstreams: ECR Public, Kubernetes registry and Quay without authentication; Docker Hub, GitHub Container Registry, GitLab.com, Azure Container Registry and Chainguard require configured credentials. A public image does not imply anonymous pull-through support for its registry. ECR private upstreams use AWS IAM. This is a supported-registry list, not a generic proxy for any arbitrary registry. Recheck AWS's list before adoption. For Ghostline, replication fits proactive release distribution and pull-through fits upstream image acquisition; neither replaces stable-release selection or compatibility testing. No mechanism selected or enabled.

## Native replication and source outages

Status: deferred by Anthony on September 21; this section describes capabilities and future considerations, not an active implementation plan.

Both registries currently return an empty replication-rule list. A proposed setup would push a validated release once into a chosen source region, match only Ghostline's repository prefix, and have ECR copy it asynchronously into explicitly selected destinations. Regional ECS image references would still point to regional repositories. [Configuration and filtering](https://docs.aws.amazon.com/AmazonECR/latest/userguide/registry-settings-configure.html).

Destination copies are retained repositories, not requests forwarded to the source. Consequently, a source ECR outage would block the normal publication/distribution path for new releases, while already copied releases would remain available for destination-region cold launches. Local builds can still run. Seeding a new destination or recovering an image absent there would need the source or an independently available copy. This availability assessment follows the separate-repository model; it is not an outage test. Removing replication settings does not delete previous copies. [Replication examples and removal](https://docs.aws.amazon.com/AmazonECR/latest/userguide/registry-settings-examples.html).

Important constraints from [AWS's replication guide](https://docs.aws.amazon.com/AmazonECR/latest/userguide/replication.html):

- Replication preserves repository names. Our current `ghostline-ecs-stockholm/...` and `ghostline-cape-town/...` names would not map to one another. Adopt common names or explicitly accept source-named destination repositories in a reviewed migration.
- Existing images are not automatically backfilled when enabling replication or adding a destination. Explicitly seed the required recorded release; future matching pushes then replicate.
- Most replication completes within 30 minutes, sometimes longer. This is AWS's typical-timing guidance, not a 30-minute SLA or maximum delay. It is asynchronous, and a successful source push is not evidence the destination is ready.
- Images replicate one hop; source-to-A plus A-to-B does not forward the original push to B. Configure destinations explicitly.
- Deletions and lifecycle policies do not propagate. Each destination needs deliberate cleanup and repository settings.

Keep destination immutability, encryption, cost tags and access controls in regional IaC, or deliberately use repository creation templates. Unconfigured automatic creation defaults to mutable tags and no repository/lifecycle policies. Templates affect newly created repositories, not existing ones. [Creation templates](https://docs.aws.amazon.com/AmazonECR/latest/userguide/repository-creation-templates.html).

Proposed release gate: validate/publish one exact artifact set; wait for each destination's expected tags and digests before allowing its rollout. Source-side [DescribeImageReplicationStatus](https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_DescribeImageReplicationStatus.html) can diagnose progress, but restart/rebuild should verify only its destination artifacts and recorded selection, without calling the source as an unnecessary prerequisite. Destinations remain ordinary repositories, so authorized direct publication could be an exceptional recovery path; preserve exact tested bytes and immutable-tag identity. This initial proposal does not add an automatic failover framework.

Replication configuration is account/region registry state, shared with other projects. Do not let multiple application stacks independently replace it: choose an owner or deliberately preserve unrelated rules during reconciliation. [PutReplicationConfiguration](https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_PutReplicationConfiguration.html). Storage and replication transfer remain billable. This was the initial research boundary; the subsequently approved implementation uses NVA/London sources and preserves unrelated rules.

September 21 destination-management clarification: reconcile the intended regional membership before a release push, preferably during regional activation, rather than adding a target in response to the push that already happened. Keep temporarily unavailable intended destinations in the configuration; transient health is not membership. A newly added destination needs an explicit copy of the selected existing release from a healthy registry. `ReplicateImage` is an internal AWS API, not a callable manual replay operation. Do not rely on re-pushing an unchanged immutable tag to generate a fresh trigger. Both possible publishers must target each destination directly because received replicas do not cascade. [Internal replication API](https://docs.aws.amazon.com/AmazonECR/latest/userguide/slr-replication.html), [copy tooling guidance](https://docs.aws.amazon.com/AmazonECR/latest/userguide/migrate-from-third-party.html).

### Source failover follow-up — September 21

AWS's documented native replication model has no automatic source promotion, global failover publishing endpoint or rerouting of a failed push to another regional registry. It does provide independent regional copies. ECR itself also has AWS-managed multi-AZ resilience inside each region; that is distinct from recovery from a whole-region outage. [AWS multi-AZ service behavior](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_withstand_component_failures_failover2good.html), [regional replication model](https://docs.aws.amazon.com/AmazonECR/latest/userguide/replication.html).

An optional design could preconfigure outgoing replication in two publishing regions, each directly targeting all required destinations. An operator or our publisher would still select the healthy region and push there; native replication does not make that choice. Receiving a replica does not trigger another replication hop. Preserve exact tested artifacts and immutable tag/digest identity, then reconcile missing copies after recovery. No such configuration or automatic publisher failover is selected.

Bidirectional clarification: two regional registries can each replicate matching repository prefixes to the other. A direct push in A copies to B without echoing back; a direct push in B copies to A without echoing back. This follows AWS's one-hop rule and needs no custom loop filter. Image restoration is also a documented trigger, so "direct uploads only" is not literally the entire trigger set. Rules belong to regional registry configuration and preserve repository names; Ghostline's current region-specific repository prefixes would need alignment. Recommend one selected publisher per release/channel promotion even with two possible origins: concurrent different writes to mutable `production` are a conflict risk, and replication is not a release-order coordinator. This is documented capability, not a live bidirectional/outage test or selected implementation. [Replication triggers and naming](https://docs.aws.amazon.com/AmazonECR/latest/userguide/replication.html).

Replication exposes IN_PROGRESS/COMPLETE/FAILED status and completion events; these help validate distribution, not promote a source. The reviewed docs do not promise indefinite retries or automatic backfill after arbitrary outages, so do not infer recovery from elapsed time. Verify destination artifacts and explicitly repair missing releases. [Status API](https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_ImageReplicationStatus.html), [EventBridge notifications](https://docs.aws.amazon.com/AmazonECR/latest/userguide/ecr-eventbridge.html). Recommendation remains a primary publication path plus an explicit regional override if needed; avoid requiring the source to restart an already seeded exit. This follow-up used documentation only, with no AWS or runtime changes.

Anthony's selected event-driven design keeps regional image sources, static `:keep-production` task references and an OCI release document in the initializer repository. A regional handler verifies the complete set and forces deployment of the unchanged CDK-owned task definition. [Release contract](event-driven-releases.md) owns the details, including the accepted tag-resolution race, limited controller authority, task-definition alerting and missed-event recovery. The subsequent implementation is recorded in the handoff and release workflow.

A second tag on the same manifest is not a second image copy. Prefer count over blanket age expiry. Stable initializer versions should not disappear merely because they are old, and parent manifest lists must retain their referenced untagged children. Native count rules use push time, not successful-release history, so protect the intended `production` image, the still-running image after a failed rollout, and any explicit rollback target outside the recent set. A `production` tag alone does not grant retention protection. Fresh activation targeting production removes the need for indefinite preservation of every parked historical release, once that behavior is implemented and validated. [Lifecycle evaluation](https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html), [rule interaction](https://docs.aws.amazon.com/AmazonECR/latest/userguide/lifecycle_policy_examples.html), [AWS warning about purging running images](https://docs.aws.amazon.com/eks/latest/best-practices/image-security.html).
