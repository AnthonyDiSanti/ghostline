## Verified AWS behavior

ECR replication is one-hop and copies only content pushed/restored after configuration. Names must match; no tag-level replication filter or retroactive backfill API exists. Source retagging is `PutImage`, not resource `TagResource`; replicated deletions and lifecycle policies are not supported. Every selected member targets other members directly and a new region is explicitly seeded. Preserve unrelated registry rules because `PutReplicationConfiguration` replaces a singleton document. [Replication](https://docs.aws.amazon.com/AmazonECR/latest/userguide/replication.html), [retagging](https://docs.aws.amazon.com/AmazonECR/latest/userguide/image-retag.html), [registry configuration](https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_PutReplicationConfiguration.html).

ECR notifications are best-effort. A schedule can repair missed wakeups but does not transfer missing bytes. EventBridge global endpoints route custom ingestion, not all native ECR events; regional rules avoid a global event-bus dependency. Source/DR outage does not affect completed local copies or existing tasks. [Delivery](https://docs.aws.amazon.com/eventbridge/latest/ref/events-ref-ecr.html), [native events](https://docs.aws.amazon.com/AmazonECR/latest/userguide/ecr-eventbridge.html), [global endpoints](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-global-endpoints.html).

ECS image version consistency captures image digests per deployment. Explicit `enabled` avoids silent reliance on defaults. It is not a transaction across three tags and does not version secret parameters. `UpdateService` has no complete IAM force-only field restriction: restrict its service resource, omit task-definition/PassRole authority, and test the request shape. [Resolution](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-type-ecs.html), [UpdateService](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_UpdateService.html).

## Rollback configuration and retention boundary

Enable native circuit breaker/rollback with the existing minimum healthy zero / maximum 100 service configuration. Fixed host ports prevent overlapping tasks; this has nothing to do with burstable CPU credits. The current service lacks application health checks, so circuit breaker evidence chiefly covers launch/startup failures. A first deployment has no completed rollback target. [Circuit breaker](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html).

### Native rollback is not an MRU fallback chain

ECS restores its most recent completed regional service revision, not `keep-mru-1`, then 2, then 3. Example: global C/B/A, regional B never succeeded; C failure can return directly to A. If that rollback fails, native ECS does not promise recursive older-image recovery. It does not retag ECR, and regional failure does not remove a release from global app history. Explicit retry or a new corrected/older-set promotion is the selected recovery path.

### MRU mechanics and tag names

The adopted names and implementation are in [release identity](../../docs/releases.md#authoritative-document-and-tags) and [retention](../../docs/releases.md#retention). Exact high-priority count-one rules protect each alias; a seven-day untagged rule and bounded observation-aware operator cleanup remove eligible leftovers. Multiple patterns in one rule are AND, not OR; wildcard count-three retention orders by push age, not app MRU. `lastRecordedPullTime` is coarse and does not establish rollback usefulness. OCI documents have no subject relationship so reusing/deleting an initializer does not implicitly erase distinct history. [Lifecycle evaluator](https://docs.aws.amazon.com/AmazonECR/latest/userguide/LifecyclePolicies.html), [image metadata](https://docs.aws.amazon.com/AmazonECR/latest/APIReference/API_ImageDetail.html).

Temporary publication aliases replicate but their deletion does not. Operator cleanup verifies complete destination aliases before removing redundant staging protection; the read-only gate never writes ECR. Retained runtime observations protect a parked or lagging host; missing observations defer cleanup rather than guessing from current aliases.

## Initializer separation review — September 27 (proposal only)

The shared initializer mainly simplifies one joint startup barrier, cleanup and container wiring; it does not save a continuously running process. It currently receives both server bundles and mounts both protocol directories writable. Two containers using the same initializer image could each receive only its own bundle and writable child mount, retaining the same five image artifacts, single ECS task/release and shared task budget. This narrows ordinary container-level secret/write exposure, not host-compromise or task IAM authority; the execution role still retrieves both bundles for ECS and application containers still have no task role. A compromised shared image can affect both instances.

Both engines can depend on SUCCESS of both initializers, preserving the existing all-configurations-ready barrier; [ECS supports multiple container dependencies](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDependency.html). Splitting does not require independent task/service rollouts or one RAM filesystem per protocol. It adds startup/container bookkeeping and potentially a higher transient memory peak if renderers run together, not another permanently resident service. The current network-disabled, capability-free shared initializer already has a narrow exposure window. Priority assessment: keep the shared initializer for now. Its brief, network-disabled, capability-free execution handles operator-controlled parameters; the engines already have protocol-private read-only mounts. Splitting would narrow initializer exposure but would not improve the ordinary running-engine boundary or host-compromise boundary. Revisit if protocol preparation gains different privileges/dependencies or untrusted inputs. This is an agent recommendation under owner review, not a newly selected architecture or implementation task.

### Shared stack and first activation

CloudFormation's ECS service DesiredCount defaults to one for creation, but omission during update preserves the existing count. Initial activation therefore explicitly supplies `EmptyGatewayOnCreate=true`, establishes management EIPs/host/bootstrap/daemon readiness, removes that setting while empty and only then starts the gateway. CLI task changes transfer the lifecycle claim before CloudFormation can wait for synchronous ECS hooks. [Service property semantics](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ecs-service.html), [UpdateService deployment triggers](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_UpdateService.html).

`cdk diff` does not accept `--parameters`; supplying it emits an ignored-option warning. Print the reviewed lifecycle parameter alongside the template diff and supply it only to deploy. [CDK diff options](https://docs.aws.amazon.com/cdk/v2/guide/ref-cli-cmd-diff.html). The live Ireland test accepted ROLLBACK and rejected ABORT even though the StopServiceDeployment API model lists both. Lifecycle preflight waits for native completion/rollback before changing power intent; do not infer support from the enum alone. [API reference](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_StopServiceDeployment.html).

### ECS deployment authorization — September 28 Ireland trial

`DescribeServiceDeployments` and `StopServiceDeployment` authorize both the exact service and its service-deployment ARN. A deployment-only grant caused an actual lifecycle hook AccessDenied, surfaced by ECS as `HookStatus must not be null`. Scope both resource types; do not grant task-definition writes. Sources: [service authorization](https://docs.aws.amazon.com/id_id/service-authorization/latest/reference/list_amazonelasticcontainerservice.html), [deployment read permissions](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-deployment-permissions.html). Empty first-service creation invokes hooks even at desiredCount zero; acknowledge only after native identity and empty-task readback.

CloudFormation host-slot qualification also established that launch templates need explicit ownership tags (`GhostlineHostStack`), not reserved CloudFormation tags; tag updates need existing-resource authorization because AWS may send only the changed keys. `DeregisterTaskDefinition`/`DescribeTaskDefinition` have no resource-level IAM support: grant only in the CFN-only role, constrained by `aws:RequestedRegion`, while keeping Lambda limited to reviewed immutable templates. See the same ECS authorization table and [trial evidence](../scratch/2026-09-28-blue-green/gateway-trial.md).

### Native ECS hook throttling

September 28 Ireland real-gateway trial: a concurrency-one controller was occupied when ECS invoked POST_SCALE_UP. Native ECS failed the deployment on Lambda HTTP 429 after one attempt and rolled back before EIP cutover. Do not connect blocking lifecycle hooks directly to the shared serialized worker. A thin receiver with independent callback capacity forwards the hook; controller throttling or a lost transport acknowledgement returns IN_PROGRESS. Only the worker mutates state/resources; genuine controller failures remain visible. See [trial evidence](../scratch/2026-09-28-blue-green/gateway-trial.md). This is distinct from safe asynchronous EventBridge retry behavior.

[CloudFormation import](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/resource-import-existing-stack.html) applies stack-level tags at import. [AWS's import introduction](https://aws.amazon.com/blogs/aws/new-import-existing-resources-into-a-cloudformation-stack/) explicitly includes automatically created ownership tags for supported resources. Still verify live stack-ID tags after retain/import; launch templates need the explicit GhostlineHostStack tag.

### Retained-resource import rehearsal — September 28

During the disposable blue-green ownership transfer, AWS rejected new Outputs and stack Tags in `CreateChangeSet(IMPORT)`. Import the exact retained resources first, then restore those stack metadata in an ordinary update. Inspect the change set and deny `Update:Replace` during ownership-only updates: a launch-template reference can report conditional Instance replacement even when resource properties are unchanged. Import did refresh the Instance/ENI reserved CloudFormation ownership tags; the LaunchTemplate provider explicitly skipped its tag update because it would require replacement. Verify each resource rather than assuming identical tagging behavior. Keep release/lifecycle exclusion throughout detachment/import and preserve a resumable exact-identity journal. See the [migration evidence](../scratch/2026-09-28-blue-green/migration.md) for the observed limits.

Source: [AWS change-set error guidance](https://repost.aws/knowledge-center/cloudformation-change-set-errors), plus Ireland live import/change-set events. This is CloudFormation ownership migration, not a host update or image qualification.

CDK CLI synthesis adds resource path/analytics metadata absent from direct `buildApp()` synthesis. Compare GatewayTask **properties**, and omit resource Metadata/the AWS::CDK::Metadata resource when classifying meaningful infrastructure changes. Otherwise a no-op can be misclassified as CDK launching a task revision, suppress the controller's force request and strand the rollout waiting for a deployment that never exists. Regression: `infra/test/infrastructure-rollout.test.ts`; live repeated-deploy qualification passed without host, boot, task or deployment turnover.

### Stopped ECS container-instance retirement

Ireland whole-host-stop failback left a disconnected ECS registration with zero running/pending counts while both tasks retained lastStatus RUNNING. EC2 stopped state proves processes ended, but ECS status alone cannot close this cleanup. Use non-forced deregistration only after exact ownership, stopped state, agent disconnection and zero counts; reobserve registration absence before retirement. Running hosts still require actual task stop. AWS additionally authorizes DeregisterContainerInstance against the enclosing cluster ARN (live AccessDenied), so grant the exact cluster plus its container-instance prefix. Do not substitute force or broader cluster permissions. [API reference](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_DeregisterContainerInstance.html). The same Ireland action completed cleanup after this correction; the subsequent full destroy/repeat-destroy and independent absence audit also passed.
