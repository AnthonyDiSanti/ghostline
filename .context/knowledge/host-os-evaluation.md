## What Bottlerocket would improve—and what it cannot guarantee

Its immutable verified root and enforced mandatory access controls reduce opportunities for host modification and constrain processes beyond Unix ownership/capabilities. Fewer built-in administrative tools reduce exposed software. Whole-image updates avoid arbitrary package-state combinations. These are stronger default host properties, not proof against a container/kernel exploit. Mutable data/settings remain, and a host-level attacker can still threaten live operational keys and traffic. No-shell is friction for an attacker, not a security boundary by itself. [Security design](https://github.com/bottlerocket-os/bottlerocket/blob/develop/SECURITY_FEATURES.md), [mutable areas](https://bottlerocket.dev/en/faq/).

AWG still needs `/dev/net/tun`, network-namespace NET_ADMIN and forwarding/NAT. Xray still needs its operational identity to serve clients. Preserve separate namespaces, no engine secret environment, read-only protocol-private mounts, no task IAM, no-new-privileges, dropped capabilities, metadata/host/peer isolation and encrypted storage. A different distribution does not remove these requirements or make ECS-injected secret metadata RAM-only.

Secure Boot is platform/AMI dependent: verify the actual t4g.small boot configuration before claiming it. Do not infer active Secure Boot merely from choosing Bottlerocket. The September 21 final trial inspection confirmed UEFI Secure Boot (`SecureBoot=1`, `SetupMode=0`) and integrity lockdown; [observed posture](../../docs/bottlerocket-trial.md#observed-evidence-and-limits) distinguishes the earlier privileged helper from the restricted ECS daemon and the subsequent coordinated OS/image update work. OS/container vulnerability counts and smaller base-image sizes are not standalone security scores. [EC2 verification](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/uefi-secure-boot.html).

## Restricting the persistent controller

The selected implementation separates finite bootstrap, continuous networking and privileged diagnostics. Removing management sockets is essential: a read-only Unix-socket mount does not make its API read-only. Bottlerocket's ordinary host containers retain the OS API socket/`control_t`; `superpowered=false` removes needed network capabilities without establishing the desired boundary. Its settings do not expose granular capability/mount/seccomp controls. ECS supplies those controls without a custom OS or a security-sensitive custom sandbox launcher. [Host runtime](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/352546d/sources/host-ctr/cmd/host-ctr/main.go), [settings schema](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/352546d/sources/api/host-containers/src/config.rs).

**Live discovery finding:** the installed ECS agent supplies task/container identity, StartedAt and RestartCount, but its bridge-mode `Networks` field is absent. Join identities to the kernel's Docker-owned TCP/443 and UDP/443 DNAT destinations, bracketed by matching ECS snapshots; validate the actual bridge subnet and exact rule shape. This uses NET_ADMIN already required for policy and avoids a Docker socket. Agent metadata files are not a safe alternative authority: `write_metadata_unix.go` mounts them writable into the engine. Source schema support is not proof the installed mode populates a field. [Introspection](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs-agent-introspection.html), [response schema](https://github.com/aws/amazon-ecs-agent/blob/master/ecs-agent/introspection/v1/response.go), [metadata mount implementation](https://github.com/aws/amazon-ecs-agent/blob/master/agent/containermetadata/write_metadata_unix.go).

**Capability finding:** NET_ADMIN alone can create IP sets and unrelated rules but fails when iptables-restore loads an IP-set matcher (`Can't open socket to ipset`). The identical isolated probe succeeds with NET_RAW. Qualify actual operations together, not individually; the initial incomplete probe missed this and the first restricted cold deployment failed before gateway creation. No policy relaxation beyond these two demonstrated networking capabilities is selected.

**Diagnostic transport:** use `apiclient exec <container> -- <command> ...`. Without the separator, apiclient can interpret the child's `-s` (iptables source address) as its own socket argument. The NAT fault test caught this before any rule mutation; add the separator consistently, not a command-specific quoting workaround. [CLI parser examples](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/352546d/sources/api/apiclient/src/main.rs).

**Early guard finding:** Docker can prepend its own FORWARD chains; a direct FORWARD guard alone is insufficient. Install the empty lease guard first in DOCKER-USER before Docker starts, maintain that order ahead of accepting Ghostline rules, and gate INPUT as well. Withdraw leases before repairing either guard or SNAT order. [Implemented boundaries and acceptance](../../docs/bottlerocket-trial.md).

### Can preparation finish and exit?

Anthony subsequently questioned whether a daemon is needed at all. Distinguish one-time platform setup from reacting to dynamic engine identities: RAM mount/permissions, bridge sysctls, host addresses and static filtering can be prepared each boot, and kernel rules do not intrinsically need a userspace process to keep operating. Current per-engine SNAT/forwarding rules embed discovered Docker bridge IPs; replacements may change or reuse those addresses. Current bootstrap runs before they exist. The controller also removes stale conntrack entries and repairs our NAT jump when Docker prepends its masquerade rule. The five-second leases are a defense for this reconciliation design, not an independent architectural reason to keep a daemon.

The static-address assessment did not identify a supported drop-in replacement; Anthony selected the daemon instead. No static bridge-IP field or lifecycle-stable identity is configured today; do not guess Docker allocation order. TCP-versus-UDP cannot classify decrypted egress because either VPN can carry both. Host networking would change AWG's NET_ADMIN boundary; engine-applied packet marks similarly need capability/identity analysis. Neither redesign is selected. [Current implementation](../../docs/ecs.md#bridge-networking), [Docker bridge behavior](https://docs.docker.com/engine/network/drivers/bridge/), [Docker firewall ownership](https://docs.docker.com/engine/network/packet-filtering-firewalls/).

A job invoked for every task/network change is another possible lifecycle mechanism, but is not one-time boot preparation and still needs reliable ordering/recovery. Simply letting today's helper configure the first engines and exit would leave stale policy after replacements (or stop forwarding when its leases expire). Do not deploy that shortcut or weaken isolation to eliminate the process. The selected daemon retains this dynamic bridge design.

September 21 follow-up: ECS supplies task-local startup dependencies, service deployment hooks and asynchronous EventBridge state events, but no documented synchronous host-network hook covering every individual engine restart. A short-lived repair job would be our orchestration: target the correct host, rediscover current identities, serialize changes, handle duplicate/stale events and recover failures. Independently restarted containers need explicit coverage; a service deployment hook alone is insufficient. [Container dependencies](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDependency.html), [deployment hooks](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-lifecycle-hooks.html), [events](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_cwe_events.html), [in-place restarts and changing bridge addresses](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/container-restart-policy.html).

ECS's current task API exposes fixed bridge host ports, but no per-container bridge IP, Docker HostIp binding or arbitrary user-defined Docker network selection. Our host private addresses/EIPs can remain stable while internal engine addresses change. `awsvpc` supplies a task ENI/shared network namespace, not a caller-selected persistent IP/ENI or separate per-engine interfaces; its API accepts subnets, security groups and public-IP assignment. Host networking would let applications bind stable host addresses, but AWG's NET_ADMIN would then act on host networking, and listening-address selection alone does not solve forwarded egress identity. No supported static-address toggle removes the current controller while preserving all existing boundaries. Keep redesigns as research, not an implementation commitment. [Container API](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDefinition.html), [port API](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_PortMapping.html), [VPC configuration](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_AwsVpcConfiguration.html), [task network sharing](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-networking-awsvpc.html), [host networking](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/networking-networkmode-host.html).

### Daemon permission budget

The maintained source separates `bootstrap.py`, `daemon.py`, `discovery.py`, shared `guard.py` and explicit `diagnostics.py`. Bootstrap/diagnostics and the restricted daemon are distinct published artifacts; the September 22 coupled image is historical. Their permission budget follows responsibility.

| Owner | Responsibility | Required authority / boundary |
| --- | --- | --- |
| Network daemon | Discover exact engine family/name, IP and restart generation; reject ambiguity/stale metadata | Local ECS introspection plus Docker-owned kernel NAT bindings; no Docker or Bottlerocket management socket |
| Network daemon | Establish/repair secondary host address, ingress/forwarding/SNAT rules and jump order; update expiring IP sets and delete affected conntrack entries | Host network namespace plus NET_ADMIN and NET_RAW, required by the qualified IP-set matcher |
| Native OS settings | Load bridge filtering modules and configure kernel sysctls | Declarative Bottlerocket settings; no daemon SYS_MODULE or OS API socket |
| Finite bootstrap | Mount host-visible tmpfs, establish directory ownership/modes and verify host prerequisites | Boot-only mount/filesystem authority; no continuing daemon SYS_ADMIN, CHOWN or host-root mount |
| ECS task definitions / app initializer | Bind protocol-private read-only directories and configure runtime confinement; restore keys before engines | Existing ECS execution-role injection and initializer write mount; daemon has no secret/config mount or task role |
| Explicit diagnostics | Inspect process labels/cgroups, enter engine namespaces and hash operational config | Keep these powers out of the production daemon rather than retaining them for its health check |

Use one idempotent network implementation for first start, daemon recovery and ongoing repair. Moving its initial network operations into a second privileged script would not narrow its continuing NET_ADMIN authority. A distinct early-boot requirement remains: quarantine must precede every engine's traffic, including Docker/ECS restoration. Keep only a minimal deny guard in essential bootstrap unless an equivalent enforced startup barrier is proven; do not duplicate full per-engine routing setup. Reuse a shared guard implementation if both boot and daemon must restore it. Expiring leases alone cannot protect the period before their firewall rules exist.

ECS runtime restrictions: privileged false, drop ALL then add NET_ADMIN and NET_RAW; no host PID namespace, devices, host filesystem or management sockets; no SYS_ADMIN, SYS_MODULE, SYS_PTRACE, DAC_OVERRIDE or MAC administration; read-only root, private small scratch, default seccomp, no-new-privileges and enforcing ordinary container SELinux policy. The daemon uses the qualified nft backend and public topology; it does not mount host root to inspect a symlink. Qualification preserves capabilities through subprocesses without a SELinux exception. [ECS capability controls](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_KernelCapabilities.html), [Linux capability definitions](https://man7.org/linux/man-pages/man7/capabilities.7.html).

NET_ADMIN is host-network-wide, not scoped to named chains, interfaces or two EIPs. The daemon can redirect/disrupt traffic and alter network restrictions; no task role does not prove host IAM credentials are inaccessible through IMDS. Treat it as a trusted host network administrator. Removing mounts/control sockets prevents direct access through those channels, but does not make traffic confidentiality or AWS credential isolation safe against a compromised controller. A narrower semantic firewall API would require a separate privileged broker/custom enforcement, not an ECS flag. No such extra component is selected.

### Conventional ECS daemon lifecycle

`DAEMON` is a service scheduling strategy: one ordinary task per eligible ACTIVE EC2 container instance, no desired count, separate from the gateway REPLICA service. It does not grant host networking or privilege automatically and does not provision/restart EC2 hosts. ECS reserves daemon resources and prioritizes their launch; orderly instance draining stops replica tasks before daemon tasks. A task-group placement constraint (`task:group == service:<daemon-service>`) can enforce placement before the gateway, but placement/RUNNING does not prove routing readiness, and `dependsOn` cannot cross tasks. Keep the bootstrap boot gate and forwarding leases. The helper must observe newly created engine IPs before permitting traffic, so full per-engine routing cannot be a prerequisite for creating those engines. [Scheduling](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_service-options.html), [placement example](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/constraint-examples.html), [container dependencies](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_ContainerDependency.html).

Helper failure is recovered independently by its service; classic DAEMON does not automatically stop the gateway or replace the host. Our leases close forwarding during that recovery. A host reboot loses RAM/rules and repeats essential bootstrap before agent recovery; the application must receive fresh initialization, and daemon migration requires repeating cold/reboot/stop-start tests. Abrupt shutdown has no graceful draining guarantee. The trial power path scales the gateway to zero, waits for termination, drains the ECS host, waits for the daemon and then stops EC2. Resume reactivates the host and verifies daemon health before starting the gateway. Scaling the gateway alone to zero leaves a daemon on an eligible active host. The 64 MiB daemon allocation moves out of the existing 666 MiB host reservation, leaving 602 MiB reserved outside ECS and the gateway budget unchanged. A temporary comparison task reserves 32 MiB with the same 64 MiB hard limit to fit alongside the old controller; that overlap setting is not the deployed daemon budget.

Do not confuse this with the newer **ECS Managed Daemons**, which apply to **ECS Managed Instances**, provide stronger startup coupling and can drain/replace hosts when a daemon fails. That is a different compute/lifecycle product from our self-managed Bottlerocket EC2 host and is not proposed here. [Managed Daemons distinction](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/managed-daemons.html).
