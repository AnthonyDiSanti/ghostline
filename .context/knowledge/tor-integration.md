# Personal Tor access and self-hosting

Historical research only: Ghostline retired the transparent gateway Tor/virtual-IP experiment on October 26. The current runtime uses shared CoreDNS for ordinary DNS and returns local NXDOMAIN for `.onion`; see [selected DNS design](../../docs/dns.md). Dated candidate and client observations below explain the retirement and do not define a current release path.

## Mullvad Browser and ordinary-client compatibility — October 18

Native Mullvad Browser on this Mac showed “Server Not Found” for the checksum-valid trial onion URL while OneXraySE was visibly connected to Ireland in All via VPN mode. A separate `https://example.com` tab loaded. Its `about:networking#dns` identified `https://dns.mullvad.net/dns-query` in DoH mode 3. Mullvad's [hard-facts page](https://mullvad.net/en/browser/hard-facts) describes browser-owned DoH for all DNS requests without fallback, and describes Mullvad Browser as Firefox-based without Tor network patches. No exact-name gateway capture or browser DoH trace was taken, so distinguish *failed navigation* from proof that no lookup occurred. No browser preferences were changed; the temporary diagnostics/control tabs were closed, leaving the failed URL visible. The pre-existing Ireland VPN connection was left intact.

[Proton's Tor-over-VPN guide](https://protonvpn.com/support/tor-vpn) is concrete counterevidence to the claim that regular browsers always need a separate proxy: it shows Edge on Windows, Chrome on Android and Safari on Apple platforms with its own VPN Tor servers. It requires Proton's kill switch on macOS/iOS, and desktop Firefox needs `network.dns.blockDotOnion=false`; Firefox iOS is documented to work without that setting. [Nord's Firefox guide](https://support.nordvpn.com/hc/en-us/articles/20283644947089-Firefox-does-not-open-onion-websites) confirms the desktop Firefox exception. These vendor reports neither identify the precise DNS/route mechanism nor qualify Ghostline's current clients. Under Ghostline, ordinary Chrome/OneXraySE and iOS Safari/Chrome already failed to supply the exact test name to gateway DNS without a local handoff. A no-extra-setup feature must be scoped to client/OS combinations proven against Ghostline, not advertised for arbitrary VPN clients.

For future research: [RFC 7686](https://www.rfc-editor.org/rfc/rfc7686.html) recommends that non-Tor applications error rather than send `.onion` to DNS, while [Chromium's proxy documentation](https://chromium.googlesource.com/chromium/src/+/main/net/docs/proxy.md) explains that a configured HTTP or SOCKS5 proxy receives hostnames before client resolution. This is why server DNS cannot recover names that never leave an application and why the October 17 PAC worked. Do not weaken Mullvad Browser's DNS/privacy settings solely to make the gateway trial pass.

## Device-scope PAC acceptance and cleanup — October 17

The top-level `PayloadScope=System` allowed a manually installed macOS `com.apple.SystemConfiguration` network-proxy profile to make a loopback PAC effective while OneXraySE ran. The PAC sent only `.onion` suffix requests to a local HTTP proxy, leaving ordinary sites DIRECT. With Ireland REALITY connected in its saved `routeOnly` custom mode, normal Chrome address-bar entry of a checksum-valid `http://…onion/` test URL displayed the gateway's exact virtual-route marker; `https://example.com` also loaded. The helper obtained a private virtual A record through VPN DNS, verified a `utun` route, and forwarded the original Host to the virtual address. Chrome automation's `goto` returned `ERR_BLOCKED_BY_CLIENT`, but native address-bar entry succeeded, so automation navigation is not a reliable acceptance action for this special-use name. This is one-device HTTP evidence for an independently installed system profile, not VPN-owned policy, HTTPS, Tor, other onion names or other protocols/devices. [Full observation](../handoff.md#native-mac-chrome-device-profile-trial--october-17).

System Settings profile removal waited at “Removing profile…” until OneXraySE disconnected. After disconnect, the profile disappeared, effective PAC was disabled and the launchd helper could be stopped. Cleanup must keep the helper alive until profile removal is confirmed, and should disconnect the VPN before treating a stalled removal as failure. Device-scope installation, local listener lifecycle, signed distribution, reconnect and interface changes remain release concerns.

## macOS device-profile alternative — October 13

Apple's [Network Proxy Configuration payload](https://developer.apple.com/documentation/devicemanagement/networkproxyconfiguration) can set device-level `Proxies` and allows manual installation on macOS. Its [Proxies schema](https://developer.apple.com/documentation/devicemanagement/networkproxyconfiguration/proxies-data.dictionary) includes `ProxyAutoConfigEnable`, `ProxyAutoConfigURLString` and `FallBackAllowed`; the latter is set to zero in the disposable test so a missing PAC server does not silently turn `.onion` requests direct. Apple's [System Settings instructions](https://support.apple.com/en-au/guide/mac-help/mh35561/mac) require review/install through Device Management; macOS `profiles` no longer installs configuration profiles. This differs from the per-physical-service and transient dynamic-store writes that failed under the active tunnel.

The top-level profile must declare `PayloadScope=System` for this device-only payload. The first manual installation omitted it and macOS rejected the payload as a user profile. Apple's [top-level schema](https://developer.apple.com/documentation/devicemanagement/toplevel) permits `System` or `User`; plist validation alone did not catch the missing semantic key. A fresh ignored `desktop-profile-probe-system.mobileconfig` was prepared with new profile identifiers to avoid cached failed downloads; the October 17 installation and effective-policy readback above completed that trial, and the file was removed afterward.

The original ignored trial profile pointed to a launchd-kept loopback PAC. The PAC's conservative JavaScript returned a local proxy for `.onion` and DIRECT for ordinary names, while the proxy accepted only the exact test onion, checked the VPN route before querying it and sent 502 while disconnected. Its October 13 preinstall checks passed; the later device-scope native result and cleanup are above. No code-signing identity or Xcode installation exists on this Mac for a modified OneXraySE extension. Signed distribution, helper startup ordering, profile removal and PAC availability still need release qualification. [Original preparation](../handoff.md#prepared-macos-device-profile-proxy-trial--october-13).

## Desktop proxy to gateway trial — October 13

The installed Mac Chrome accepts the checksum-valid `pg6mmjiyjmcrsslvykfwnntlaru7p5svn6y2ymmju6nubxndf4pscryd.onion` URL when given a loopback HTTP proxy. In a disposable headless profile with a process-only proxy argument, Chrome rendered a local exact-host marker; the proxy observed the absolute-form onion request. This narrows the earlier normal-profile `ERR_BLOCKED_BY_CLIENT` result: Chrome's network stack can hand off that hostname, but the source of the earlier block was not identified.

With OneXraySE's saved `routeOnly` profile connected to Ireland, the Mac routed ordinary and `100.127.57.89` traffic through `utun8`, ordinary HTTPS returned 200, and the public exit matched the trial REALITY EIP. A loopback exact-host proxy queried `pg6...onion` with `dig @8.8.8.8` through the tunnel, validated its one A answer in the configured virtual `/16`, checked the `utun` route, and connected to its port 80 with the original Host. Curl and disposable headless Chrome both received the exact gateway marker; the proxy saw HTTP 200 from the gateway. This proves an end-to-end desktop HTTP request can cross the native REALITY tunnel and virtual-IP route when a browser proxy supplies the name. It does **not** prove automatic proxy selection, HTTPS CONNECT, an installed helper lifecycle, or Tor access. The exact-host probe and Chrome profiles were deleted afterward.

A bounded PAC write to `State:/Network/Global/Proxies` while the tunnel was active had no effective `scutil --proxy` result; the injected value was absent on readback, and a fresh Chrome process received no marker. The reconciliation mechanism was not identified. This and the prior physical-service PAC failure rule out those particular preference writes as the lifecycle mechanism. OneXraySE was disconnected, its original All via VPN choice restored, and direct `en0`/ordinary HTTPS 200 verified.

For the next signed-client experiment, prefer `NEProxySettings.matchDomains = ["onion"]` with an exact loopback HTTP/HTTPS proxy over writing physical or dynamic-store proxy preferences. Apple documents [suffix matching](https://developer.apple.com/documentation/networkextension/neproxysettings/matchdomains), [tunnel proxy settings](https://developer.apple.com/documentation/networkextension/netunnelnetworksettings/proxysettings), and [PAC JavaScript](https://developer.apple.com/documentation/networkextension/neproxysettings/proxyautoconfigurationjavascript). The `proxySettings` discussion limits its claim to hosts in the tunnel's internal network. The installed [OneXray `buildSettings`](https://github.com/YuanDevTeam/OneXray/blob/main/swift/Tunnel/PacketTunnelProvider.swift) sets DNS and routes but no proxy policy. **Inference:** an app-owned proxy policy could avoid per-interface races and be removed atomically with the tunnel; only a native Chrome trial can establish whether macOS applies it before `.onion` resolution fails. A helper outside the extension is favored for virtual-IP sockets because the process-only proxy on the host has already traversed the tunnel; an extension-originated socket has not been tested. The helper must couple its readiness and lifetime to the specific VPN session, reject arbitrary destinations, re-resolve each onion connection through tunnel DNS, check route/pool identity, preserve HTTP Host or CONNECT authority, and fail closed on service or mapping loss. These are design requirements, not tested implementation.

## Ireland native Chrome and virtual-pool conflict — October 13

The native Mac OneXraySE trial proves two separate limits. While connected to the Ireland DNS candidate, ordinary Chrome HTTPS and the REALITY egress IP passed. ### Maintained ECS integration boundaries — October 12

The [release model](../../infra/lib/releases/model.ts) defines five runnable artifacts and validates their exact count in schema v3. The [regional gateway task](../../infra/lib/ecs-stack.ts) starts two essential engines after one secret-bearing initializer. The [host network policy](../../runtime/ecs/network.py) drops all Docker bridge peer traffic before allowing engine Internet egress; [discovery](../../runtime/ecs/bottlerocket/discovery.py) and daemon qualification currently expect the two named engines. A required DNS image/container therefore changes the complete release contract, task definition, validated peer set and host guard together. Merely adding a container or repository would not create a usable or secure path.

Migration must keep already-published five-image documents readable for historical retention and actual parked/running dependencies, while new complete releases require the DNS image. Do not fabricate a DNS descriptor inside an old release or treat it as a six-image rollback candidate. The exact protected-history and runtime-retention rules need an explicit schema-aware transition and isolated publication/rollback tests before any production alias moves.

On October 12, `parseRelease` was pinned to the five historical image names for schema v2/v3, and a test rejects a sixth descriptor in those documents. A read-only v4 schema now requires exactly those five plus `dns-policy`, with a distinct manifest media type. Schema-aware identity, protected-history checks and cleanup protect the right descriptors per record. The existing five-image publication and runtime gates explicitly reject a v4 current selection; this is a reader/repository precursor, not permission to move aliases or treat an old release as a DNS-enabled rollback candidate. Test publication, protected history and parked-region launch against both schemas during the actual migration.

The common image builder can also prepare a DNS candidate with the exact `dns-policy.Dockerfile`, `dns-policy.py` and shared `dns-policy.json` bytes and a content-derived ARM64 tag. The installed `images:build` selection and five-image publisher are unchanged; neither promotes this candidate. The package boundary is covered by a source test and the image itself passed a separate local ARM64 Docker build and isolated runtime health checks.

### Proposed whole-stack migration sequence — October 12

The October 12 REALITY-source proposal below describes the original trial design and deployed Ireland image. The October 26 decision selects the host ENI primary address for future DNS egress; see [current DNS assessment](dns-forwarder.md#shared-egress-identity--selected-october-26).

The existing host guard SNATs each discovered container IP to its assigned protocol EIP. Anthony selected **one shared DNS container and one DNS egress identity**. Source now generates a host rule that SNATs only that authenticated container's DoT egress to the existing REALITY EIP; AWG and REALITY application traffic retain their own EIPs. This avoids a third allocation and keeps `.onion` queries local. It requires native readback of both protocols' DNS answers and independent verification that DoT leaves via the intended EIP. No DNS rule or sidecar is deployed yet.

The migration needs an **operator-only continuation mode** before aliases move. The existing `held` release-stack mode disables every non-hook gate invocation; the normal CLI blue-green path hands ownership to that gate and then invokes it to finish, so merely holding automation would strand the rollout. Source now has a `manual` mode that suppresses ECR/hourly selection while permitting a nonterminal rollout to continue only with its persisted controller claim; a stale claim cannot select a new release. Explicit held cleanup and cleaned retry remain available, and native hooks remain enabled. Focused source tests pass. This control is not yet cloud-deployed or lifecycle-qualified, so it cannot be used for the migration until isolated native proof.

With that gate in place, the proposed sequence has explicit readbacks at each phase:

1. Add a new release schema with an exact DNS image descriptor and schema-aware loops for availability, copy, alias rotation, protected history, retention, runtime observation and equality. Old v2/v3 documents keep their five-image meaning; they are not valid rollbacks for a DNS-required task. Qualify mixed-schema retention and rollback behavior offline before cloud work.
2. Add the DNS repository and v4-capable release/controller readers across every enrolled member while gateway tasks still use the old definition. Put gateway regions into tested operator-only mode before moving any production aliases. Read back that mode and old active task/host identities.
3. Centrally qualify and distribute the complete DNS-bearing image set. Publish its new document/aliases with automatic selection suppressed; verify every member has the exact descriptors and protected old runtime images. Do not synthesize a DNS descriptor for old releases or let a partial replication trigger rollout.
4. Deploy the updated ECS task, restricted network daemon/discovery and private DNS adapters through the existing CLI-prepared green host and native ECS blue-green path. Keep blue on the old task for rollback until green proves DNS, ordinary browsing, both protocols, EIP identity, isolation and lifecycle recovery. A parked region receives the new intent and definition without waking; verify its retained images and later cold launch separately.
5. Restore automation only after each regional state is coherent, then exercise normal no-op reconciliation, stop/park/rebuild and retained-release cleanup. Publication and CDK deployment remain distinct owners; an operator-only delivery mode is a general maintenance control, not a compatibility branch for old task definitions.

This is a source-review plan, not a completed release, deployment or native-client acceptance. The exact controller behavior with held automation and a changed task definition requires isolated tests before any production alias move.

The selected shared container uses one DoT egress identity: the existing REALITY EIP. The source-tested host policy now generates exact Cloudflare/Google port-853 allows from the same JSON file consumed by the resolver, and SNATs only the discovered DNS peer to that EIP. ### DNS control versus FakeDNS — October 4 assessment

[Xray FakeDNS](https://xtls.github.io/en/config/fakedns.html) answers an intercepted name lookup with a temporary virtual IP and records its domain mapping. The connection to that IP must then re-enter Xray's tunnel with FakeDNS sniffing enabled so Xray can restore the original hostname before routing. It is a hostname-recovery mechanism for IP-based application traffic, not interception by itself. Xray supports a domain-scoped FakeDNS server rule, which is preferable to returning fake addresses for all domains during this `.onion` trial. The mapping is per running Core instance and can become stale in the OS or browser cache after reconnect. [OneXray documents the cache and bypass limits](https://onexray.com/docs/configuration/dns/).

The current Mac tunnel advertises Google DNS over TLS. [OneXray separates platform tunnel DNS from Xray route DNS](https://onexray.com/docs/advanced/vpn-tunnel/), so enabling FakeDNS only in a route does not prove that Chrome's system query will reach it; application-owned DoH/DoT and applications that refuse `.onion` before querying are additional limits. For the next native trial, first prove which resolver receives the synthetic Chrome `.onion` lookup using a disposable client configuration. If Xray receives it, try `.onion`-scoped FakeDNS plus tunnel delivery/recovery and the same private shim; verify normal-domain and reconnect controls. An explicit browser SOCKS/PAC path is a simpler comparison for Chrome because it sends the hostname without DNS synthesis. Do not change the accepted system tunnel DNS or production gateway as a shortcut to this proof.

For AWG, the same virtual-address idea needs a different owner. Current [AWG profile generation](../../infra/lib/awg.ts) advertises Cloudflare DNS and sends IP packets through the tunnel; it does not convey the queried hostname or OneXray's local FakeDNS mapping. An AWG-transparent design would direct supported clients' `.onion` lookups to a controlled resolver, retain the name-to-virtual-IP mapping at the gateway, and deliver subsequent TCP connections for that range to the same private shim or future Tor path. [Tor's `AutomapHostsOnResolve` documents this kind of temporary mapping](https://blog.torproject.org/coming-tor-026/). Reusing a OneXray FakeDNS setting on the device cannot make an AWG gateway recover the name from an IP packet. Client-owned DoH/DoT, pre-DNS refusals such as direct curl, mapping lifetime and multi-device isolation still require separate checks. A browser SOCKS/PAC path bypasses this DNS problem and can work over either full-device VPN protocol, but needs browser configuration on each device. The isolated AWG test below validates the mapping and packet path, not a production DNS/network change.

### Shared DNS direction — October 4 design assessment

No per-site entries are required. A suffix rule can intercept all queried names under `.onion` and allocate a distinct virtual address on demand. Xray's `domain:onion` test did this for two names; [Tor's `AutomapHostsOnResolve` and `AutomapHostsSuffixes`](https://manpages.debian.org/experimental/tor/torrc.5.en.html) provide the same class of on-demand mapping when Tor is present. DNS mapping applies only to applications that actually query the controlled resolver; [RFC 7686](https://www.rfc-editor.org/rfc/rfc7686.html) allows non-Tor applications to refuse `.onion` before DNS.

Prefer one **policy and mapping owner** for supported device DNS across protocols if native clients can reliably send their DNS and subsequent virtual-IP connections through the VPN. A private resolver would handle ordinary names through a selected encrypted upstream, reserve `.onion` locally without forwarding it, and return virtual addresses. The same component (or Tor instance whose DNSPort created the mapping) must then receive virtual-IP TCP connections, recover the hostname and send it to Tor. A DNS-only sidecar or one shared IP for every onion name would lose the destination identity. Tor's `DNSPort` plus `AutomapHostsOnResolve` and `TransPort` are a candidate for the onion mapping/connection pair, but need isolated routing and restart qualification; `DNSPort` handles only A/AAAA/PTR and its default virtual IPv4 range is loopback, unsuitable as a VPN-client range without explicit configuration. [Tor client-port and virtual-network reference](https://manpages.debian.org/experimental/tor/torrc.5.en.html).

Keep protocol-specific adapters small. AWG can advertise an in-tunnel resolver address and route virtual-IP packets to the mapping owner. Xray needs a qualified path for OneXraySE's platform DNS and IP-only TUN connections across REALITY; its current VLESS link does not configure those. [OneXray distinguishes platform Tunnel DNS from Xray's route DNS](https://onexray.com/docs/configuration/dns/) and Apple DoT requires the advertised server name to match the resolver certificate, so changing only the gateway or only one client DNS field is insufficient. If a native Xray client cannot use the shared gateway DNS path, client-side Xray FakeDNS remains a protocol-specific adapter: it must recover the hostname *before* VLESS, after which the gateway can route by domain. Reproducing Xray's private FakeDNS map in AWG is not useful; AWG sends IP packets and needs the gateway-owned map.

A shared service is not a blanket network exception. Ghostline's ECS bridge isolates its Xray and AWG engine namespaces and blocks sibling access; expose only the specific DNS and virtual-address flows and preserve separate protocol egress EIPs. The resolver/mapping state needs bounded TTLs, per-device isolation or equivalent ownership, restart/cache recovery, and fail-closed behavior for unmapped virtual IPs. For DNS privacy, test that system UDP/TCP 53 stays inside the active tunnel, `.onion` never reaches an upstream resolver, ordinary upstream DNS follows the chosen encrypted path and protocol EIP, and reconnection/VPN-down behavior matches the intended policy. App-owned DoH/DoT may bypass the selected DNS policy even when its packets still traverse the VPN; blocking port 53 alone cannot prove comprehensive DNS control. No shared DNS component, Tor sidecar or native-client configuration has been selected or deployed.

## Product value and scope — October 3 assessment

Bundled gateway Tor is a useful access feature when the goal is to open `.onion` sites from supported devices without separately installing Tor. [Proton VPN's Tor servers](https://protonvpn.com/support/tor-vpn) demonstrate that regular-browser Tor access is a viable product pattern, though its implementation does not establish Ghostline compatibility. This is an access and convenience benefit, not a claim that the VPN adds Tor anonymity or that a regular browser gains Tor Browser's privacy protections. [Tor Project warns about using other browsers](https://support.torproject.org/tor-browser/security/using-tor-with-other-browsers/).

The useful Ghostline scope is optional `.onion` access over an existing VPN profile, with ordinary destinations retaining their current egress. A separate all-traffic Tor mode is a simpler fallback if selective behavior proves too fragile, but it changes everyday performance and application compatibility: [Tor's SOCKS interface has no UDP support](https://spec.torproject.org/socks-extensions), and Proton warns that its Tor servers are slow. Either option requires an explicit supported-client/browser contract; the current Mac Chrome/OneXraySE path failed before gateway routing could help. Prove client delivery and a real onion connection in an isolated trial before adding Tor to the shared ECS task or coupling it to on-demand lifecycle. This is an engineering recommendation, not an approved implementation or a universal-device promise.

## What a self-run node would add

| Node type | Value for this goal | Boundary |
| --- | --- | --- |
| Tor client on the device, using Tor Browser or local SOCKS on macOS | Supports `.onion` access with device-side circuits; Tor Browser adds browser anonymity protections | Circuit and onion-service authentication start at the device; Chrome needs selective proxy configuration and leak testing |
| Tor client on the Ghostline gateway | Could proxy selected applications through Tor | Circuit starts on AWS; Ghostline sees pre-Tor requests; ordinary browsers gain no Tor Browser protections |
| Private bridge on an independently reachable host | Could restore reachability when direct Tor and available bridges are blocked | Entry/circumvention point, not an extra anonymity layer or an exit |
| Public relay/exit or hosted onion service | Different operational goals | Explicitly outside this product scope |

Tor Project says [running a relay can improve anonymity in some threat models, with uncertain tradeoffs](https://support.torproject.org/relays/getting-started/better-anonymity/). Its example depends on carrying other people's traffic, which a personal-only bridge or Tor client does not provide. A [bridge is an unlisted entry relay](https://support.torproject.org/relays/getting-started/what-is-a-bridge/); its concrete benefit here is reachability and making Tor entry harder for a local network to identify/block. It does not replace Tor's remaining relays or make an `.onion` circuit cryptographically stronger. [Onion-service circuits do not use exit relays](https://support.torproject.org/glossary/), so an owned exit would not help this goal. These conclusions about Anthony's topology are design inferences, not measured Ghostline outcomes.

## Device-side Tor alternative

Tor Browser includes its own local Tor client on Mac; [Tor Browser includes what it needs for Tor browsing](https://support.torproject.org/about-tor/using-and-sharing/torifying/), so a second local daemon is unnecessary for that path. Tor chooses its normal guard and circuits. [`.onion` service authentication and end-to-end encryption](https://support.torproject.org/tor-browser/features/onion-services/) come from the Tor connection and onion protocol; they do not require Tor Browser's anti-fingerprinting features. Tor Browser also adds browser-side anonymity protections against fingerprinting, tracking state and leaks. Those protections matter when Anthony wants to avoid linkage/identification, but a `.onion` address by itself does not establish that need. On iOS, Tor Project recommends Onion Browser but notes that its WebKit constraint prevents equivalent Tor Browser privacy protections; assess that separately rather than promising parity.

The intended active-VPN path is Tor Browser → its local Tor client → Mac full-device VPN → Ghostline exit → Tor guard or bridge → Tor network/onion service. The browser-to-client hop stays local; the outbound Tor connection should follow the VPN's actual route. With the VPN disconnected, Tor Browser can connect directly or use a bridge; this design does not make VPN presence mandatory. A VPN drop could move later Tor connections to the direct route, so a VPN-required policy would need separate OS-level enforcement. Verify both Xray and AWG native routes, Tor bootstrap, `.onion` access, disconnect/reconnect and sleep behavior before claiming this path works on the examined network. Ghostline needs no Tor container, listener, DNS interception or third EIP for this baseline.

Use a staged access check: try Tor Browser directly, then its [available bridges](https://support.torproject.org/tor-browser/circumvention/connecting-from-censored-regions/), then compare it through Ghostline if that route is useful. [Tor Project cautions against assuming a VPN improves Tor anonymity](https://support.torproject.org/tor-browser/general/vpn-with-tor/). Verify the actual client route, Tor bootstrap and an `.onion` connection before relying on the combination. A private self-run bridge is worth revisiting only if these paths are inadequate or if an independently controlled fallback is a stated requirement. Hosting a bridge on the same on-demand Ghostline host would share its power/availability failure and require a new public service; it would add little independent access value.

A Tor client on the gateway is a reasonable convenience path for `.onion` access across supported VPN clients. The Tor circuit would begin after Ghostline decrypts the VPN, so the host and its operator can observe pre-Tor destination metadata. [Tor Project describes that trust boundary for a remote Tor client](https://support.torproject.org/little-t-tor/getting-started/tor-client-central-server/). Keeping the Tor client on the device better matches an anonymity-focused browser goal and avoids adding Tor configuration, DNS handling, resource use and release/health coupling to the shared ECS task.

## Chrome `.onion` access across either VPN protocol

Anthony would also like `.onion` addresses entered in Chrome to reach the site conveniently. Automatic Tor Browser handoff is acceptable but remains an optional client feature after Tor Browser-over-VPN access works. Chrome could instead use selective local Tor SOCKS routing; that would need a managed local Tor SOCKS endpoint and greater leak/state evaluation. Either approach is shared Mac client plumbing, with separate Xray and AWG route/lifecycle acceptance. No extension, helper or browser installation is selected. [RFC 7686](https://www.rfc-editor.org/info/rfc7686/) makes `.onion` a special-use name outside normal DNS and says applications without Tor support should error rather than query DNS. A gateway cannot reliably discover `.onion` intent from arbitrary VPN packets after the app has rejected the name or hidden DNS inside another encrypted channel.

Chrome does not inherently prohibit a `.onion` URL when an appropriate proxy is configured. An isolated October 3 probe of installed Chrome 154.0.8037.95 used a disposable profile, local PAC server and fake local SOCKS5 listener: Chrome delivered the full 56-character `.onion` hostname to SOCKS as a connect request. The probe did not load a site, install Tor Browser or prove absence of every DNS path. [Chromium's SOCKS documentation](https://new.chromium.org/developers/design-documents/network-stack/socks-proxy/) says URL hostnames pass to a SOCKS5 proxy but other browser components may resolve names directly. Chrome has no Tor path in Ghostline's current client setup, so typing `.onion` there does not yet provide access.

Access-focused Chrome candidate: run a local Tor client with a SOCKS5 listener and use [Chrome's PAC/proxy configuration](https://developer.chrome.com/docs/extensions/reference/api/proxy) to send `.onion` HTTP(S) requests to it while other Chrome requests keep their normal VPN route. Specify no `DIRECT` fallback for `.onion` if the Tor client is unavailable. The isolated probe proves that Chrome can pass the hostname to SOCKS, not that this complete setup is leak-free. Test typed addresses with or without an explicit scheme, links, redirects, Tor bootstrap, proxy failure, no public `.onion` DNS attempt and actual VPN routes under both protocols. [Chromium notes](https://new.chromium.org/developers/design-documents/network-stack/socks-proxy/) that some browser components can resolve names outside the URL proxy path. This option retains Chrome's cookies, extensions and browser fingerprint; [Tor Project recommends Tor Browser](https://support.torproject.org/tor-browser/security/using-tor-with-other-browsers/) when anonymity from websites matters.

Browser-privacy candidate: a narrowly scoped Chrome extension detects top-level HTTP(S) `.onion` navigation, prevents the Chrome network request, and passes the exact URL to a local native-messaging helper that opens Tor Browser. [Chrome declarativeNetRequest](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest) supports request blocking; [native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging) supplies the local-app boundary. This needs an isolated interception/handoff trial before implementation. Tor Browser would load both onion and ordinary destinations over Tor once opened, including links followed there. Tor Browser was not found in `/Applications` on the examined Mac.

## Why gateway routing is a separate design

| Selection point | Xray/VLESS path | AWG path | Security/compatibility limit |
| --- | --- | --- | --- |
| Tor-aware app on device | Tor Browser builds its own circuits; its guard traffic uses the active full-device VPN | Same | Works independently of the Ghostline protocol, but Tor Browser sends its ordinary websites through Tor too |
| Per-host application proxy on device | A capable app could send `.onion` hostnames to a local Tor SOCKS client and leave other traffic on the active VPN | Same | Browser/PAC/OS behavior requires native tests; an ordinary browser lacks Tor Browser's privacy defenses |
| Gateway Tor client | [Xray can route a domain](https://xtls.github.io/en/config/routing.html) to a [SOCKS outbound](https://xtls.github.io/en/config/outbound.html) only if its client preserved the `.onion` hostname | AWG gives the server IP packets, so this would need controlled DNS interception, Tor virtual-address mapping and TCP redirection | Current AWG profiles point DNS at public resolvers; apps may suppress `.onion` DNS or use encrypted DNS, so this cannot be a universal server-only switch |

Tor's [`DNSPort`/`AutomapHostsOnResolve`](https://manpages.debian.org/unstable/tor/torrc.5.en.html) can map a `.onion` name to a virtual IP for applications that actually query that listener; `TransPort` can redirect corresponding TCP. This is an explicit client-DNS plus gateway-networking design, not passive recognition of every `.onion` URL. It would need profile/DNS changes for both protocols, per-client mapping/isolation, fail-closed routing, and proof that chosen Mac/iOS apps issue the required requests. Tor's [SOCKS interface does not support UDP](https://spec.torproject.org/socks-extensions), so arbitrary AWG UDP cannot be passed through it. [Tor discourages ordinary browsers over Tor](https://support.torproject.org/tor-browser/security/using-tor-with-other-browsers/) because DNS, WebRTC, fingerprint and browser-state leaks remain possible.

Device-side Tor remains an independent access path. For the REALITY-wide goal, qualify hostname delivery and the browser/client path before selecting gateway implementation. Mac Chrome proxy/extension designs do not transfer directly to iOS.

## Lifecycle interaction and next evidence

The future lifecycle lease should use authenticated Ghostline protocol presence/activity, not Tor daemon uptime, bridge reachability or Tor circuit churn. Tor Browser used directly or through an independent bridge creates no Ghostline lease. When it runs through Ghostline, it is ordinary authenticated VPN traffic; an open but silent browser is still not reliably visible as active. Decide whether Tor browsing needs an explicit keep-running hold or permanent mode, and treat stale observer telemetry as unknown rather than idle. A stopped gateway still needs the independent authenticated start path described in [lifecycle research](on-demand-lifecycle.md).

Before any deployment, compare direct Tor, Tor-provided bridges and Tor over each Ghostline protocol on the actual Mac/network. Verify `.onion` access, the client route, VPN disconnect/restore and quiet-session behavior without collecting browsing destinations. Test iOS separately if selected. Only a demonstrated access gap should lead to a private-bridge design and its own lifecycle/cost boundary.
