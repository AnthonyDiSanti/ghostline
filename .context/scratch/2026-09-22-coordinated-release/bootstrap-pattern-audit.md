# Bottlerocket bootstrap pattern audit — September 23, 2026

The Ireland failure is a boot availability failure, not evidence of credential exposure or a bypass of Ghostline's isolation. Confidence is high that the **reproduced containerd client path** has a snapshot lease defect. Confidence is lower that GC caused the original single boot failure, because that boot lacked a GC trace. No audit can certify every part of this advanced deployment with 100% certainty.

| Interface | Expected pattern and Ghostline observation | Assessment |
| --- | --- | --- |
| ECS host | Official `aws-ecs-3` ARM64 AMI with the native ECS agent; normal ECS gateway and separate DAEMON tasks run only after native bootstrap. | Supported variant. The selected daemon/app ordering is enforced by explicit health/lifecycle checks, not inferred from CloudFormation dependencies. |
| Early host work | One finite `mode="always"`, `essential=true` bootstrap container establishes RAM storage and empty forwarding quarantine before ECS. It exits; it has no application credentials or Docker discovery. Generic kernel/ECS settings remain native settings. | Matches Bottlerocket's documented per-boot and essential lifecycle. Its mount under `/.bottlerocket/rootfs/mnt` uses the documented shared mount area. It does not edit the immutable OS or `/etc`. |
| Image source | A valid ARM64 OCI image in ECR, selected through the native `source` setting. Both A and B ran successfully on other boots and share valid cached layers. | OCI manifests sharing layers are ordinary, not a malformed-image exception. Moving a mutable selector and rebooting is an advanced availability choice: the native host runtime must still pull, and the earlier ECR 403 test proved no guaranteed cached fallback. This merits continued qualification even after the snapshot repair. |
| Failure boundary | Native `host-ctr` logged pull/unpack success and failed to create the bootstrap container with a missing parent snapshot before our entrypoint. | Our RAM/firewall code, ECS tasks and app release controller did not execute at the failure point. `essential=true` correctly prevented unsafe workload restoration. |
| Native defect | The exact core-kit 16.3.0 `host-ctr` still pulls then separately unpacks. Controlled GC after cached-layer `Stat` reproduces success from `Image.Unpack` followed by a missing parent on the actual host snapshotter; leased and `WithPullUnpack` controls pass. | Strong evidence for an upstream client-path problem. It does not retroactively prove the original boot's GC timing; the [upstream issue](https://github.com/bottlerocket-os/bottlerocket-core-kit/issues/1059) asks maintainers to validate the cause and repair. |

Versioned 1.64 docs describe the relevant API; exact 1.65 runtime behavior comes from the Ireland observations.

Selected disposition: keep production and current aliases unchanged. Do not ship a patched OS, disable verification, make bootstrap optional, or automatically replay the paused action. Watch issue #1059 and official core-kit/Bottlerocket release notes at major work-unit transitions. An issue closure or a higher version number alone does not pass the gate. Identify a reviewed fix in an official ECS-3 ARM64 release, then test its native A→B bootstrap replay, repeated boot, controlled recovery, confinement and full central qualification in Ireland before production migration. Continue unrelated source/product work against the existing qualified production architecture meanwhile.
