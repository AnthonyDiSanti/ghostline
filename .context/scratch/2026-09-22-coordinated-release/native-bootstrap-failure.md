# Native bootstrap replay failure — September 22

Status: recovered disposable host; a matching native snapshot-GC failure mechanism is now reproduced with a candidate upstream API repair. The original boot had no GC timing trace, so causality in that exact event is not proven. Candidate native qualification remains withheld. Production stays on the previously qualified coupled helper and v1 release selectors.

## Observation

The deployed regional Lambda passed application-only, daemon-only and combined changes on Ireland's common-stack host `i-0829da3981f4f5b2f`. The combined update changed bootstrap B→A. A subsequent bootstrap-only A→B update issued one reboot at 13:43:52 UTC. Bottlerocket 1.65.0's native `host-ctr` pulled the image successfully, returned from unpack and then failed to create `boot.ghostline` at 13:44:13: parent snapshot `sha256:43a4975922edae064cd56015aad7b7d3444b6fcf2ce51b2b22a9964e4c53b8f0` did not exist. Our bootstrap entrypoint never ran. Essential boot ordering prevented ECS restoration.

Both candidates share the same three rootfs layers; only OCI configuration labels differ. A's index is `885ed429…`, B's is `968a53c9…`. The actual native runtime server and CLI are `2.2.7+bottlerocket`, revision `7835c8dfefceee63b1a4f9e84e015ddc8434fdc3`; matching core-kit 16.3.0 host-ctr imports containerd client 1.7.33. These are distinct versions, not interchangeable evidence.

The controller waited for its bounded observation deadline and paused at the reboot step. CloudTrail shows no repeated reboot. One separately journaled diagnostic reboot at 13:59:39 recovered the same host and B bootstrap, then the daemon and gateway. Original EIPs and credentials remain unchanged. Diagnostics were disabled and administrative lockdown verified in cleanup. The failed release attempt remains paused rather than being relabeled complete.

## Bounded diagnosis and limits

An isolated `ghostline-snapshot-probe` native runtime namespace passed eight alternating A/B pulls, unpacks and snapshot creations/removals. The test used a temporary ECR alias, removed afterward, and never executed a bootstrap entrypoint or changed serving aliases/services. Its local image cache remains only on the disposable disk. This did **not** reproduce the boot failure and does not prove a repair. No additional blind reboot sequence, cache deletion, signature bypass, optional bootstrap or unit override was applied.

The first eight tests had no controlled GC boundary, so passing them did not test the race. On September 23, a synthetic OCI reproducer using `containerd` client 1.7.33 and server 2.2.7 forced synchronous GC after the cached-layer `Stat` in the legacy separate `Image.Unpack` path. Unpack incorrectly returned success, then creating a child snapshot failed with the same missing-parent error class. Explicitly leasing the cached snapshot prevented deletion. The standard `Pull(..., WithPullUnpack, WithPullSnapshotter(DefaultSnapshotter))` path also survived the same forced GC: its unpacker protects an existing snapshot through `Prepare` before checking `Stat`.

The same controlled test then passed against the **actual Ireland Bottlerocket host-containerd 2.2.7 overlayfs snapshotter**. A temporary derivative of the exact bootstrap B image carried only the diagnostic binary. The test used isolated containerd namespaces, changed only the disabled-by-default diagnostic source, and ran no bootstrap entrypoint or gateway rollout. An extended control forced another synchronous GC after `Pull` returned and its temporary lease ended, before child creation; the candidate path still retained the snapshot. A test-harness retry first collided with a namespace from the previous run; fresh unique namespaces resolved that collision. The final run passed. All temporary diagnostic ECR roots and their exact child tags were removed after confirming no other aliases; the diagnostic source was restored to `keep-production`, admin/diagnostics were disabled, and all three regional gateway/daemon pairs read back running with no pending tasks. Private final results: `.local/coordinated-release/native-gc-final/{receipt.json,result.log}` and `/tmp/ghostline-native-gc-final-readback.log`. The unprotected case again produced `Unpack=<nil>` followed by `parent snapshot … does not exist`; the protected and upstream pull/unpack controls succeeded.

This confirms a real defect in the selected legacy client path and a successful candidate API change on the native runtime. It strongly supports, but cannot retroactively prove, the GC timing of the original failure. It does **not** qualify a patched Bottlerocket OS: native `host-ctr` runs before our bootstrap image and is part of the verified OS. A small [upstream source patch](host-ctr-pull-unpack.patch), also [publicly available](https://gist.github.com/AnthonyDiSanti/3a31dd18a14dff65c21b2153fb550a30), applies cleanly to core-kit 16.3.0 and current `develop`, adds unpack to `Pull` with the existing snapshotter, and removes the separate `Image.Unpack`. Its isolated `develop` Go tests pass. No replacement OS, unit override, security relaxation or production change was deployed. Shipping this repair requires a supported upstream Bottlerocket release or a separately chosen and qualified OS delivery strategy; ordinary Ghostline image publication cannot replace `host-ctr`.

A sanitized [upstream report](upstream-host-ctr-issue.md) was submitted as [core-kit issue #1059](https://github.com/bottlerocket-os/bottlerocket-core-kit/issues/1059) after Anthony requested reporting. The local [pattern audit](bootstrap-pattern-audit.md) found no invalid bootstrap use explaining the pre-entrypoint failure. No pull request, patched OS or production change was submitted.

The native [`bootstrap-commands` API](https://bottlerocket.dev/en/os/1.63.x/concepts/bootstrap-commands/) is not a drop-in escape from host-ctr. It runs only `apiclient` operations before bootstrap containers and cannot execute our RAM, ownership and forwarding-quarantine code or `apiclient exec` at that stage. A custom Bottlerocket build would also require an independently owned AMI and TUF update source rather than remaining on the official stable update channel; see the [official build guide](https://github.com/bottlerocket-os/bottlerocket/blob/develop/BUILDING.md). These are material architecture/security ownership decisions, not a code-only patch to this repository.

The September 23 authenticated public-metadata check still identifies official [v1.65.0](https://github.com/bottlerocket-os/bottlerocket/releases/tag/v1.65.0) as latest stable (published September 9). No newer stable OS carrying this repair is available through that channel. This is a bounded release check, not a claim that no upstream development exists.

September 23 decision: Anthony selected an official Bottlerocket fix before promotion, not a custom OS or a cold-rebuild workaround. Keep the current production hold and security boundaries. Monitor the issue and official releases; a new version alone does not establish a repair.
