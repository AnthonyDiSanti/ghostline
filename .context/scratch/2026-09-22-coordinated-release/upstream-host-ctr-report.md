Issue title: `host-ctr: unpack during Pull so cached snapshots stay leased`

Bottlerocket 1.65.0 (`aws-ecs-3`, ARM64; core-kit 16.3.0) failed once to restart an essential bootstrap container after its image selector changed between OCI manifests sharing filesystem layers. The native `host-ctr` log showed a successful pull/unpack, followed by `parent snapshot sha256:… does not exist: not found` while creating the container. The bootstrap entrypoint had not run. A subsequent reboot recovered the same host. The original boot did not capture a GC event trace.

The matching host-ctr source calls `client.Pull` without `WithPullUnpack`, then separately calls `img.Unpack(ctx, DefaultSnapshotter)` and `NewContainer` with a new snapshot. In containerd client 1.7.33, the legacy cached-layer path checks `Snapshotter.Stat` without first adding that existing snapshot to the unpack lease. An isolated reproducer forces synchronous GC immediately after that check. `Image.Unpack` returns nil, but the next child snapshot fails with the same missing-parent error class. This reproduces with containerd server 2.2.7 using both a private native snapshotter and the actual Bottlerocket host-containerd overlayfs snapshotter on an isolated test host. Explicitly leasing the cached snapshot survives GC.

The existing `client.Pull(..., WithPullUnpack, WithPullSnapshotter(DefaultSnapshotter))` path survives the identical forced GC on both snapshotters. Its parallel unpacker uses `Prepare` with `containerd.io/snapshot.ref`, protecting an existing snapshot in the lease before the cached-layer check. Another synchronous GC **after Pull returns and its temporary lease ends**, but before child creation, still leaves the snapshot available. The proposed [minimal patch](host-ctr-pull-unpack.patch) moves unpack into Pull and keeps the same default snapshotter; it applies cleanly to core-kit 16.3.0. Pull retries would then also cover unpack failures. This is a candidate fix, not a qualification of a rebuilt Bottlerocket OS or proof of the exact GC timing in the original boot.

For maintainers: please review whether this API change preserves schema-1 conversion, registry resolver and labels, and whether a regression test can force GC between the cached-layer check and container creation. The private test harness uses synthetic OCI blobs and isolated containerd namespaces; no credentials or customer image data are required to reproduce the mechanism. We can provide a trimmed reproducer if useful.
