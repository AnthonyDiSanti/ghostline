# AL2023 bridge: boot-gate-first trial

Status: both disposable trials complete and torn down. **Shell-user-data installation failed; a derivative official-base AMI with the gate preinstalled passed the synthetic first-boot boundary.** Production Stockholm and Cape Town remain on Bottlerocket 1.65; Ireland's separate paused Bottlerocket diagnostic host was untouched. The real five-image AL2023 runtime is not yet ported or qualified.

## Trial boundary

- Source: [official ECS-optimized AL2023 ARM64 recommended AMI](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/retrieve-ecs-optimized_AMI.html), resolved through its regional public SSM parameter on new launch. The selected Ireland image was `ami-00ee2e7d1fc75cba8` (`al2023-ami-ecs-hvm-2023.0.20260918-kernel-6.1-arm64`, Amazon owner `591542846629`). The actual stock Docker unit did **not** order itself after `cloud-final.service`, despite ECS doing so.
- Trial stack: `GhostlineAl2023BootGateTrial` in Ireland, its own VPC/cluster/t4g.small/30 GiB encrypted root/public IP, zero ingress and no gateway service, application credentials, EIP or production dependency. The ECS instance role may register only in the dedicated trial cluster.
- User data installed versioned repo-owned systemd units and scripts. The ECS cluster setting was the final step after package/unit verification, so the failed installation did not enroll the host in its target cluster. **That did not make first launch safe enough:** Docker started before the drop-in existed. Once installed, Docker required the RAM mount and ran empty quarantine in `ExecStartPre` on every restart/boot, then a finite exact-digest probe gated ECS. The probe tested boot ordering, not the real Bottlerocket-specific bootstrap image.
- Inspect first launch, second boot, failed package/unit installation, failed image pull, and a Docker `--restart=always` bridge sentinel across reboot. Assert no protocol forwarding before the daemon (or after bootstrap failure), correct private RAM and no unintended ECS registration. Recover by restoring the selected image and rebooting; test stop/start. Preserve synthetic evidence without secrets.
- If the gate is sound, adapt the real bootstrap image/observation and host tool backend, then add daemon/gateway, release-document OS compatibility, memory/GuardDuty checks, complete lifecycle/teardown and central qualification. Diff production stacks before any retained-IP cold rebuild. If first-boot or restored-container safety is unprovable, stop the bridge and compare a baked host image with waiting for the official Bottlerocket repair.

From `infra/`, `npm run trial:al2023-gate synth` and a fresh Ireland diff preceded deployment. Ireland lacked the usual CDK bootstrap roles/parameter, so this asset-free trial used CLI-credential synthesis; the final manifest contained no deploy/CloudFormation execution roles or bootstrap version. This is trial machinery, not a serving-path selection.

## Native result — September 24

- First launch on instance `i-0584828a1474d1066`: Docker entered active at **13:33:06 UTC**; user data wrote its Docker/ECS drop-ins at **13:33:33**. Docker's `ExecStartPre` had no run timestamp, `DOCKER-USER` contained only Docker's `RETURN`, and `cloud-final` failed on the explicit missing-Docker-order assertion. ECS began at 13:33:37 from a queued job despite the newly installed dependency, but its dedicated role could not register in the trial cluster. This is a genuine first-boot scheduling gap; IAM denial is a second boundary, not a substitute for quarantine.
- With the units already present, an explicit Docker restart ran quarantine successfully and mounted the **2 MiB** tmpfs with `65532:65532:0700`; `DOCKER-USER` placed `GHOSTLINE_LEASE` before `RETURN`. A restricted, bridge-network `--restart=always` synthetic container was then used for restoration tests.
- On the next boot, Docker's quarantine ran at 13:38:02; Docker restored the sentinel at 13:38:04; the finite probe completed and ECS started at 13:38:05. Boot ID markers matched, the lease set remained empty, and the sentinel's outbound TCP/443 timed out. ECS registered in the dedicated cluster. No gateway or network-daemon workload was deployed.
- Replacing only the probe URI with an intentionally absent public digest made the next boot fail closed: quarantine and RAM mounted, the restored sentinel remained blocked, bootstrap failed, and ECS stayed inactive. Restoring the valid digest and rebooting recovered bootstrap/ECS. A separate EC2 stop/start also replayed quarantine, bootstrap, ECS and blocked sentinel traffic successfully.
- The disposable `GhostlineAl2023BootGateTrial` stack was destroyed. Its instance is terminated, cluster INACTIVE, and stack-tagged VPC and EBS volume inventories are empty. No EIP, regional gateway, application credential or production resource was touched. These results do **not** qualify the real five-image AL2023 runtime or the first-launch shell-user-data pattern.

Anthony selected the derivative AMI trial. The first-launch proof and its limits follow; never revive the installer-first serving path.

## Derivative official-base AMI trial — September 25

- The source was Ireland's current Amazon-owned ECS-optimized AL2023 ARM64 AMI `ami-0c95e506a8160c2a1` (`al2023-ami-ecs-hvm-2023.0.20260922-kernel-6.1-arm64`). The disposable builder had no ECS enrollment authority. Its late user data installed versioned repo fixtures for Docker's RAM/quarantine pre-start gate and ECS's finite-bootstrap dependency. The early host adapter did **not** bake an ECS cluster or application secrets. It selected an exact public synthetic probe image; the real bootstrap image remains a separate artifact to port. The builder was stopped and cleaned before `CreateImage`; the trial AMI `ami-02a33f2b6dc68ead0` had a 30 GiB encrypted-root snapshot `snap-0b57534b24f7f0909`.
- The installed `cloud-init` 22.2.2 lacks `clean --machine-id`. The initial cleanup command stopped ECS/Docker/containerd and removed their per-instance data, then failed on that flag. We completed cleanup with `cloud-init clean --logs --seed`, truncated `/etc/machine-id`, removed remaining transient logs/preparation script, and verified the baked gate before stopping the builder. The repo fixture now encodes this supported sequence. AWS's [ECS optimized AMI customization guide](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/image-builder-tutorial.html) and [image hygiene guidance](https://docs.aws.amazon.com/imagebuilder/latest/userguide/security-best-practices.html) inform the cleanup; this bounded manual image is not the final reproducible production pipeline.
- A fresh host from that AMI initially exposed a **launch-only systemd cycle**: stock `ecs.service` orders after `cloud-final.service`, while the trial cloud-final script synchronously waited on `systemctl start ecs`. The gate was already installed and ran correctly, but cloud-init/ECS could not finish. We destroyed that host, changed the launch script to `systemctl --no-block start ecs.service`, ran a fresh diff and deployed a second fresh host from the same AMI. Its first boot finished cloud-init and registered in the dedicated trial cluster.
- On that fresh first boot, quarantine ran at 27.47 seconds; Docker began loading containers at 28.02 seconds; the finite **container** bootstrap finished at 34.25 seconds; ECS started at 34.29 seconds. The 2 MiB tmpfs was `65532:65532:0700`; `DOCKER-USER` entered `GHOSTLINE_LEASE` before `RETURN`; `GHOSTLINE_LIVE` had zero members. The host's direct HTTPS test returned HTTP 301, while a restricted Docker bridge sentinel timed out connecting to the same address.
- Reboot restored the sentinel only after quarantine (5.14s versus Docker load at 5.76s), replayed the finite bootstrap container and ECS, and kept the sentinel blocked. Substituting an absent public digest caused bootstrap failure and ECS dependency failure while Docker restored the still-blocked sentinel. Restoring the valid digest and starting ECS recovered without disabling the guard. An EC2 stop/start replayed RAM/quarantine/bootstrap/ECS and again blocked sentinel egress. This proves the synthetic host boundary, not production routing or protocol behavior.
- The builder and both derived hosts are terminated; the trial stack no longer exists. The trial AMI was deregistered and its encrypted snapshot deleted after verification. No real gateway service, EIP, application credential or production resource changed. The separate paused Bottlerocket Ireland diagnostic resources are unaffected. The trial used the repo's `runtime/ecs/al2023/` fixtures and `infra/bin/al2023-boot-gate-trial.ts`; they are isolated from production deployment commands.

Next: port the **real** bootstrap container and host backend to AL2023, create a provenance-controlled derivative-image build/update process, and test the full daemon/gateway, secrets, RAM, forwarding, GuardDuty, coherent release, destroy/redeploy and OS-update behavior in a disposable region. Only then consider one retained-EIP production cutover at a time. AL2023's writable host/permissive default SELinux remain explicit security tradeoffs, not permission to relax container/network confinement. Continue the official Bottlerocket #1059 watch independently.
