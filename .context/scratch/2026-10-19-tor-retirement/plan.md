## DNS reassessment — October 19, 2026

October 26 correction: one shared resolver needs no new EIP. The Ireland trial already SNATs DNS DoT to the existing REALITY private address/EIP, and both protocol paths delivered ordinary DNS to the shared resolver. The remaining work is acceptance of a maintained replacement resolver and DNS-only lifecycle, not reproving the basic shared routing. CoreDNS is the recommended candidate for Cloudflare-first/Google-fallback forwarding; Amnezia's dev DNS image actually uses Unbound. [Assessment](../../knowledge/dns-forwarder.md).

Anthony reopened the ordinary-DNS decision before removal. This plan is provisional: do not tear down the Ireland trial or delete the shared resolver until the independent DNS security value and acceptance criteria are settled. The maintained AWG profiles specify Cloudflare resolvers and full tunnel routes, which protect ordinary DNS on the device-to-gateway leg but do not request DoH/DoT on gateway egress. The maintained REALITY exports contain no DNS policy; the current Mac OneXraySE screen retains `8.8.8.8` / `dns.google` tunnel fields, while the separate Apple DoT switch and query-level behavior remain unverified. Engine containers use explicit Cloudflare DNS addresses, not an encrypted transport. The trial DNS policy can provide strict Cloudflare DoT with Google fallback, but this alone does not prove client capture or justify retaining onion mapping and virtual routes. Reassess ordinary-DNS-only design and native verification before choosing source or cloud cleanup order.

Anthony now prefers DoH originating at the VPN client and accepts DoT or DoH from the gateway to the upstream recursive resolver. Treat the device-to-gateway and gateway-to-upstream legs separately. Xray/OneXray can use a DoH URL for its route resolver, but the imported REALITY link does not impose whole-device DNS; Apple tunnel DNS is a separate DoT feature. An AWG `DNS =` address cannot encode a DoH URL. A shared resolver can own upstream policy for both protocols, but protocol/client-specific delivery still needs native qualification. DoH inside an already encrypted VPN does not alter the censor-visible outer VPN protocol. No architecture is selected yet.

Upstream-only assessment: if encrypted resolver egress is required for both protocols, prefer one private DNS forwarding container over a forwarder embedded in AWG plus separate Xray DNS behavior. AWG cannot convert forwarded port-53 packets to DoT itself; Xray's built-in DNS can use DoH but its hijack path does not transparently handle every DNS record type. Reuse the trial's narrow private port-53 ingress, explicit upstream allowlist and fail-closed egress, while removing virtual addresses, HTTP sink, virtual leases/routes and onion release behavior. Consider a maintained forwarder such as CoreDNS rather than retaining the trial's bespoke DNS wire parser. One shared instance uses one upstream egress identity and failure domain; two instances of one image are an option if separate protocol EIPs become a requirement. Keep upstream health separate from local process health so an external DNS outage does not trigger repeated whole-gateway replacement. This is a proposal, not a selected release design; native/client acceptance and the six-image release path remain necessary.

## Decision and boundary

Anthony asked to plan full removal of gateway Tor/.onion support. The intended no-extra-setup browser experience did not pass native client tests. No Tor client or egress container was deployed. The implemented experiment is a shared ordinary-DNS resolver, intercepted port-53 routing, virtual `.onion` IPv4 mapping, HTTP marker, six-image release candidate and isolated Ireland infrastructure. Maintain the existing five-image Stockholm/Cape Town VPN design and its current explicit public DNS resolvers. A separate DNS security project needs a new benefit and acceptance case; the present candidate should not be kept as a speculative foundation.
