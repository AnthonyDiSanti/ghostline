# Private DNS policy and virtual onion routing

Historical trial record only. The gateway Tor/virtual-IP design was retired; the maintained runtime uses the ordinary shared CoreDNS resolver described in [the current DNS contract](../../../docs/dns.md). Present-tense statements below describe the trial at their dated observation points.

Ghostline's intended `.onion` access path has a private DNS policy container shared by AWG and REALITY. It resolves ordinary names through certificate-checked DNS-over-TLS (DoT), assigns local virtual IPv4 addresses to queried `.onion` names, and owns the corresponding address-to-name map. Tor will be a separate container and is **not installed**. The current virtual HTTP listener returns a harmless marker; HTTPS closes without forwarding.

| --- | --- |
| Starting | Make the loopback listener ready before publishing tunnel proxy settings; refuse onion forwarding until the selected VPN session and virtual route are confirmed. |
| Connected | Apply the proxy only to the `.onion` suffix; validate the full v3 name, query gateway DNS for each new connection, require a virtual-pool answer and this session's tunnel route, then forward HTTP Host or HTTPS CONNECT authority without substituting the onion name. The DNS policy's process-local virtual mapping can assign a stale cached IP to a different name after a restart. HTTP checks Host against the live map; a local replacement test deliberately reuses one virtual address for a different name and confirms that the stale Host gets no marker while the new name succeeds. The future HTTPS/Tor adapter must verify the original destination name (for example, SNI or an authenticated helper prelude) **before** forwarding, and fail closed when it cannot. Browser, helper and gateway restart/rollout tests must cover this cross-name safety boundary. The local HTTP check does not qualify HTTPS, arbitrary non-browser TCP clients or a live blue-green handoff with cached addresses.

## Implemented component

The historical `runtime/ecs/dns-policy.py` (retired; retrieve from git history), the shared [upstream policy](../../../runtime/ecs/dns-policy.json) and its [image recipe](../../../runtime/ecs/dns-policy.Dockerfile) implement the resolver and temporary connection sink. The container has no protocol keys, task role, public DNS listener or destination-query log. DNS listens on UDP and TCP port 5353 inside a private bridge. The optional virtual router binds TCP 80/443 and installs a container-local route for the configured pool, now `100.127.0.0/16` in source; it starts with `NET_ADMIN`, `SETUID` and `SETGID`, then runs as UID/GID 65532. The outer host must route the virtual range only to this container and admit DNS and virtual traffic only from the authenticated protocol engines. DNS-only mode can run as UID/GID 65532 with all capabilities dropped.

Queries under the `.onion` TLD never go upstream; the bare `onion` apex also stays local and returns NXDOMAIN. A-record queries below the apex get a process-local mapping, capped at 4096 names with a 30-second TTL; other record types get no answer. Addresses are not reused while the process runs, and a new process starts at a random offset. That offset does **not** guarantee safety across a restart: a stale client address could overlap a new mapping. The HTTP sink checks the Host header against the mapped name; a production Tor adapter must likewise verify the requested hostname or fail closed. Ordinary queries use [Cloudflare](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-tls/) `1.1.1.1`, then `1.0.0.1`, followed by [Google](https://developers.google.com/speed/public-dns/docs/dns-over-tls) `8.8.8.8` and `8.8.4.4` on port 853. TLS verifies `one.one.one.one` or `dns.google`, respectively. Transport failure, REFUSED or SERVFAIL tries the next server; a valid NXDOMAIN is returned as-is. No plaintext upstream fallback exists. The resolver checks request shape and upstream transaction/question identity, caps concurrent handlers at 64, truncates large UDP answers for TCP retry, and returns SERVFAIL if all configured upstreams fail. Its `health` action checks both local DNS transports against the special-use apex without relying on upstream availability; the conditional ECS task uses it as the container health check.

The sink returns an HTTP marker only when both the virtual destination and Host header identify the same mapped name. It does not accept an unrelated hostname or make an Internet/Tor connection. HTTPS currently closes. This is a routing proof, not `.onion` website access.

## Protocol adapters and release work

The separate DNS owner is deliberate: AWG transports IP packets and must redirect tunnel DNS to the private resolver, then route virtual destinations to the same mapping owner. Xray can route DNS requests and virtual-IP connections to it from its REALITY inbound. Anthony selected one private DNS container shared by both protocols. The deployed isolated native trial routed its DoT traffic through the REALITY EIP private address; the source now selects the host primary address as described above. AWG and REALITY application traffic retain their own EIPs. The isolated trial uses adapters without changing maintained production. Source synthesizes an essential DNS member of the shared ECS task only for a `dnsRequired` deployment setting; the private Ireland catalog enables it, while no maintained target does. Both engines depend on its local UDP/TCP health, and the host daemon receives the same setting. The remaining gates are native browser hostname delivery, normal publication and removal of the temporary migration setting after the new recipe is adopted. Do not append an untracked sidecar or publish an image outside the release unit.

The maintained source includes DNS peer rules that remain inactive in Stockholm and Cape Town: engine port-53 DNAT to the discovered resolver, bridge-only DNS access, four-address DoT egress through the host primary address, and port-53 fail-closed behavior when DNS is required but missing. Discovery checks one resolver's paired TCP/UDP Docker bindings and identifies its bridge veth through the kernel neighbor/FDB. The host also generates a guarded direct route for the configured virtual pool, limited to engine TCP 80/443 and return packets from that exact DNS veth and original connection. It rejects conflicting routes, drops virtual packets without a resolver and suspends virtual acceptance during route reconciliation. The maintained region catalogs do not activate these rules. The isolated Bottlerocket Ireland task qualified native bridge routing with the current `100.127.0.0/16` pool before and after a selected-service blue-green rollout; native browser hostname delivery remains untested on that final host.

The conditional task uses the same bridge, memory cap and execution role as the existing gateway. DNS has no server secret, task role or engine configuration mount; it retains only NET_ADMIN to install its container-local virtual route, NET_BIND_SERVICE for 80/443, and SETUID/SETGID to drop to UID 65532 after startup. The task definition gives it an essential local health check and the engines a HEALTHY dependency, as supported by [ECS task health checks](https://docs.aws.amazon.com/AmazonECS/latest/APIReference/API_HealthCheck.html) and [EC2 task dependencies](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters_ec2.html). The host's metadata port 55353 remains blocked externally by the security group and raw host rule. Runtime observation demands the exact DNS image, running/HEALTHY container and daemon-confirmed peer for schema v4; target-scoped release readiness now admits an exact six-image selector for a DNS-enabled deployment, while publication remains blocked.

The virtual-IP connection path cannot simply reuse DNS DNAT. In a disposable two-container Linux bridge probe, host DNAT delivered synthetic TCP but the receiving container could not recover the original virtual destination through `SO_ORIGINAL_DST`. A direct `/16` route in a disjoint benchmark range then passed both forward and guarded return packet checks, and the receiving socket retained the virtual IP. The first `/16` attempt lost to the trial's existing overlapping route; the maintained policy now rejects overlapping routes before enabling virtual acceptance. [Probe and cleanup evidence](../../knowledge/tor-integration.md#proposed-whole-stack-migration-sequence--october-12).

Only plaintext DNS that reaches the tunnel can be redirected at the gateway. A device or app using independent DoH/DoT, or rejecting `.onion` before a lookup, may bypass this path. A VPN client may also ignore a profile's DNS setting. Native AWG and OneXraySE/Chrome tests must prove the actual lookup, connection and ordinary browsing before this becomes a supported device feature. The future Tor adapter must take the verified mapped hostname and forward only the selected TCP stream to a private Tor client. It must fail closed if the map or Tor client is unavailable; keep Tor outside the DNS process.

## Native phone capture — October 5, 2026

The isolated host has `tcpdump` and `nsenter`. A bounded, read-only capture on the AWG container's `awg0` interface filtered the phone peer's port-53 packets and virtual-range TCP packets. It emitted only aggregate counters and packets matching the harmless test name, with no general DNS browsing log. The first 150-second window recorded 10 phone DNS packets but no packet for the Tor-specification `.onion` name or virtual-IP connection; Anthony reported a Safari error, but the exact page-load time was not independently recorded. A second window missed the phone's next handshake by about 34 seconds.

A third ten-minute window recorded one phone DNS packet, no matching query and no virtual-IP connection for a new checksum-valid address. Anthony confirmed opening that URL during the window. The final test was synchronized: after Anthony said the phone was ready, the capture reported `ready=1`; he then opened a second new checksum-valid address in Safari and reported an error. The phone sent **40 other port-53 DNS packets** through AWG, but **none matched the exact test `.onion` address, and no virtual-IP connection appeared**. That narrows this native path to a client-side hostname-delivery boundary before the gateway resolver. The capture did not inspect encrypted app-owned DNS and cannot assign the refusal to Safari, iOS name resolution or Amnezia's DNS integration. [RFC 7686](https://www.rfc-editor.org/info/rfc7686/) says non-Tor applications should error without DNS lookup for `.onion`, which is a plausible explanation rather than a proven iOS implementation detail.

A gateway DNS rule or Tor container cannot process a name that never arrives. Preserve the VPN-level, no per-browser-configuration requirement while evaluating whether supported clients can provide a Tor-aware hostname handoff or device-level proxy. Further gateway implementation should wait for a qualified client path. The capture process and temporary sanitized counter file were removed; the trial containers, broad DNS DNAT and virtual routing remain up. No production, Mac system network or Tor change occurred.
