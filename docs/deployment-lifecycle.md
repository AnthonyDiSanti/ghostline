# Regional lifecycle

Regional lifecycle operations share durable exclusion with native ECS blue-green deployment. Stop retains the host, park retains endpoint IPs, and destroy removes owned regional runtime/release resources. Read the [handoff](../.context/handoff.md) and launch records for observed deployment state.

One reusable ECS gateway recipe serves every configured region. An explicit target controls shared regional infrastructure, two reusable host-slot stacks, one transient-address stack during overlap, and separate durable image/release infrastructure. The catalog allocates nothing by itself. [Development](development.md) lists commands; [secrets](secrets.md) defines durable identities.

| Operation | Compute | OS/data disks | Two EIPs | Images / parameters |
| --- | --- | --- | --- | --- |
| `ecs <target> stop` | Stopped, no running task | Retained | Retained | Retained |
| `ecs <target> start` | Same host; new task initialization | Reused | Reused | Reused |
| `park <target>` | Removed | Removed | Retained in stack | Retained |
| `ecs <target> unpark` (or `deploy`) | Fresh host/task | Fresh | Reused | Reused |
| `destroy <target>` | Removed | Removed | Explicitly released | Images removed; Standard parameters retained |

Regional GuardDuty protection is separate from all gateway operations: the discovered regional detector stays enabled through stop/park/destroy without any application CloudFormation ownership. See [GuardDuty](guardduty.md) for ownership, telemetry and residual monitoring costs.

Stop waits for gateway termination, drains the registered host and waits for the ECS daemon to terminate before stopping EC2. Start checks complete local production intent and unresolved failures, waits for host health and a healthy replacement network daemon, then restores one desired task without a separate force deployment. Parking uses the same EIP logical identities; a later active deployment reuses them. Destroy journals exact allocations/stack ARN, waits for deletion and verifies ownership/attachment before release. These operations preserve protocol credentials.

A stopped host avoids compute charges but keeps disk and public-address charges. Parking removes the disk cost as well; retained addresses remain billable. Completed destroy removes endpoint resources, local ECR contents and active regional application control-plane resources. Existing expiring logs/messages can still occupy storage, and independent account security can continue billing by design. Running costs include EC2, disk, public IPv4, egress and possible burstable CPU-credit charges. Do not infer a current regional price quote from an old estimate. [EC2 stop/start](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/how-ec2-instance-stop-start-works.html), [AWS public IPv4 pricing](https://aws.amazon.com/vpc/pricing/).

Use stop for a frequently reused exit, park when keeping known client addresses is worth their idle cost, and destroy for disposable regional experiments. Releasing addresses requires new profile endpoint exports after redeployment. The current client format uses literal IPv4; DNS-based persistent endpoints are not implemented.

## Exclusion and resumable destroy

A conditional DynamoDB lifecycle record coordinates the regional release controller and CLI deploy/start/stop/park/destroy. Power intent remains stopped/parked between operations, so arrivals never wake it. CLI receipts contain nonsecret ownership tokens; an interrupted operation retains its claim and resumes with the same command. Locks do not expire merely because an AWS outcome is uncertain. The controller holds its claim through ECS deployment completion; completion events and hourly reconciliation settle it. Direct AWS administration is outside this cooperating-actor contract.

Destroy writes an atomic `.local/deployments/<target>/regional-cleanup.json` with exact stack ARNs, resource identities, volume/EIP IDs, former membership, phase and pending work. It verifies account/ownership, independently adequate shared audit coverage and deployed expiring-log retention before quiescence. It first verifies native ECS deployments are terminal and acquires lifecycle ownership, then disables regional events/new gate invocations and waits out existing invocations. Stop/park/destroy refuse an unfinished native deployment before changing power intent; allow its completion or resolve rollback first. AWS rejects the ABORT stop type, so lifecycle commands do not use it or steal an active release claim. It removes incoming/outgoing owned replication rules across the union of former/current members, preserves unrelated filters, reads rules back, and reports unreachable sources or queued copies as incomplete.

Both host slots and their disks are included in the ownership journal. Gateway and daemon shutdown preserves management/EIP connectivity until actual task termination and host removal, followed by address detachment and ENI deletion. After endpoint removal and owned EIP release, cleanup removes the regional release/platform/asset stacks, retained repositories and images, nonexpiring release table, and exclusively owned Lambda asset objects/bucket. CDKToolkit and other projects are outside the ownership inventory. NVA/London remain explicitly retained publication members and cannot be destroyed by this command.

Existing seven-day CloudWatch/S3 logs and up-to-fourteen-day dead letters remain without their producers/pollers/alarms. Retained log groups and queues use CloudFormation-generated physical names, so redeployment allocates new names without collisions; old groups need no active sweeper. Standard credentials, GuardDuty and the independent CloudTrail baseline persist. No extra snapshot/archive system is created. Repeat cleanup verifies absence and can re-enter bounded cleanup for late replicated repositories; it does not equate API success with an instantly zero AWS bill. Rebuild explicitly seeds the protected release window and reuses credentials.

## Replacement and validation

Activate/seed the complete regional release before initial deployment. All five image repositories and the release-document repository survive park and are included in complete destroy. Ordinary image publication uses the [regional release gate](releases.md); centrally qualified image updates do not repeat protocol tests at each destination. Use explicit `verify` and real encrypted `test` for independently selected infrastructure/connectivity validation. Meaningful image, native setting, layout and qualified OS changes prepare a green host with its own ENI and temporary addresses, then hand off the permanent EIPs after readiness. The same ENI is never attached to two hosts. IAM shutdown dependencies keep agent authority available while services/tasks drain.

New hosts resolve the regional official ECS-3 ARM64 AMI for the centrally qualified release target version, verified by Amazon publisher alias, architecture and exact image name in preflight. OS upgrades are qualified centrally and delivered through the same green-host replacement. Both server/client parameters must exist before deployment; imports refuse identity conflicts. [OS policy](platform.md#os-policy).

## Blue-green deployments — direct EIPs and ECS lifecycle hooks

Every meaningful application, daemon, bootstrap, qualified OS or host-template change uses temporary green capacity. Unchanged releases do nothing. Separate protocol EIPs preserve ingress/egress identity; there is one host at steady state and no load balancer. The shared bridge task, initializer/engine boundaries and restricted network daemon remain unchanged.

CDK owns shared infrastructure, task definitions and EIP allocations. Reusable host-slot templates own each generation's ENI, EC2 host and placement-constrained daemon. The regional controller owns EIP associations and submits only immutable CDK templates through a scoped CloudFormation role. It cannot register task definitions, launch arbitrary instances, read application parameters or run arbitrary host commands. [Detailed authority](releases.md#controller-authority-and-audit).

1. **Prepare green before deployment.** Under the lifecycle claim, create its network and temporary EIPs, launch the centrally qualified official OS, and verify current bootstrap identity plus healthy cold daemon. Source blue keeps serving traffic.
2. **Let ECS start the gateway.** Select green for new placement and request one headless BLUE_GREEN deployment. The PRE_SCALE_UP hook confirms preparation; initializer SUCCESS gates both engines. Later hooks verify actual task/revision/digest identities and daemon-validated forwarding peers before allowing traffic movement.
3. **Move both production EIPs.** The PRODUCTION_TRAFFIC_SHIFT hook journals direction, reconciles exact bindings and moves the primary management address last. Temporary EIPs move onto blue to preserve management reachability. The swap is not atomic, and TCP/connection-tracking state is not transferred; clients may reconnect.
4. **Observe and use native rollback.** Keep blue alive through the five-minute ECS bake. Two spaced verified green failures or a bounded deadline request one native rollback, only with verified healthy blue. Reversed ECS traffic weights authorize the same hook to return the EIPs. Unknown health pauses action; there is no multi-release fallback cascade or automatic reboot loop.
5. **Retire after authoritative success.** Drain both old services, verify actual termination, then remove blue's host/disks, detach temporary addresses, remove its ENI and release those addresses. A failed green remains for explicit diagnosis/cleanup and daily cost reminders; retained infrastructure does not guarantee retained running tasks or RAM.

ECS owns deployment outcome and stage sequencing. Its direct AWS_LAMBDA hooks wait for SUCCEEDED, FAILED or IN_PROGRESS. A thin receiver has only controller-invocation authority and returns IN_PROGRESS when the concurrency-one controller is busy; otherwise native ECS treats HTTP 429 as hook failure. Durable DynamoDB state spans callbacks/stages and excludes conflicting CLI operations. Completion events and an action-only minute continuation schedule supplement hourly reconciliation. Ordinary EventBridge events do not block ECS. [Headless ECS](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/blue-green-deployment-implementation.html), [Lambda hook contract](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/lambda-lifecycle-hooks.html), [deployment events](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/ecs_service_deployment_events.html).

Readiness includes fresh OS/bootstrap, ECS task/revision, initializer, engine digest and daemon forwarding evidence. It is not a permanent authenticated internet canary. Real encrypted protocol tests qualify changes centrally; delivery does not retest them in every region. [Release state machine](releases.md#regional-state-machine) defines deadlines, uncertainty, inactive-region protection and explicit failed-generation cleanup. Stop/park/destroy wait for native deployment completion or resolved rollback before changing power intent.

Ireland qualification covers successful handoff/bake/retirement, task-loss and whole-host-stop rollback, partial two-IP failure, retained/imported ownership, no-op deployment and complete lifecycle/rebuild. [Evidence and limits](../.context/scratch/2026-09-28-blue-green/gateway-trial.md). The one-time production ownership transfer is historical evidence in [migration notes](../.context/scratch/2026-09-28-blue-green/migration.md), not a second provisioner.

Existing any-member ECR replication distributes the complete centrally qualified release to each region. Cloud publication/build scheduling and qualification of new Bottlerocket versions remain upstream work; blue-green supplies deployment orchestration. It does not introduce a competing release owner. [Distribution](releases.md#ownership-and-distribution).

## GuardDuty telemetry lifecycle

Where live regional/AZ discovery supports runtime telemetry, `EcsEndpointStack` owns the regional `guardduty-data` interface endpoint and its security group. Otherwise the stack omits telemetry transport, installer authority and enrollment while retaining the same VPN architecture. [Availability policy](guardduty.md#live-availability-and-reduced-protection). The host depends on endpoint creation: GuardDuty automatic agent management reuses that transport, and CloudFormation deletes it only after host termination during destroy/park. No teardown poller, custom resource or account-wide monitoring toggle is required. AWS documents both [reuse of IaC-created endpoints and the unmanaged-endpoint deletion problem](https://docs.aws.amazon.com/guardduty/latest/ug/using-iac-with-gdu-automated-agents-runtime-monitoring.html).

The September 20 Northern Virginia inspection recorded AWS's automatic settings: IPv4, private DNS, an explicit deny for principals outside our account, inbound TCP 443 from the VPC CIDR and no outbound rules. Our endpoint preserves those DNS/IP/policy boundaries and narrows ingress to the gateway host's security group. CloudFormation would turn an empty outbound list into default allow-all; the template uses CDK's standard no-traffic ICMP sentinel (`252/86` to `255.255.255.255/32`) to preserve blocked initiated egress. Endpoint reply traffic is stateful. Cost tags use `System=shared`; omit `GuardDutyManaged=true` because CloudFormation owns these resources.

Each Ghostline endpoint stack creates its own dedicated, non-default VPC; there is no peering or transit routing to other workloads. The GuardDuty endpoint and its private DNS are confined to that VPC in this topology. An endpoint is VPC-scoped, with interfaces in selected subnets (at most one subnet per AZ), not isolated to its placement subnet. Every VPC route table already has a [local route](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-route-tables.html); security groups and network ACLs enforce reachability. GuardDuty's default VPC-CIDR ingress can admit other hosts within that VPC without adding routes. [Interface endpoint behavior](https://docs.aws.amazon.com/vpc/latest/privatelink/create-interface-endpoint.html).

The host grants `ssm:GetManifest` for the AWS-managed GuardDuty Distributor installer; this internal API has no resource-level IAM scope. The package also requires `ssm:DescribeDocument` and `ssm:GetDocument`, scoped only to AWS’s regional `AmazonGuardDuty-RuntimeMonitoringSsmPlugin` document (empty account field in its ARN). Do not attach the broader `AmazonSSMManagedInstanceCore` policy: the host must retain no Parameter Store read access. The first two test hosts exposed a pre-existing missing-permission failure; endpoint presence alone does not prove agent coverage. The completed policy passed automatic cold-host installation of agent v1.17.1 and `HEALTHY` coverage on September 20. Verify coverage separately from installer success; reporting is asynchronous. [SSM permission reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_ssm.html).

The endpoint has [no additional usage charge, including when created manually](https://docs.aws.amazon.com/guardduty/latest/ug/creating-vpc-endpoint-ec2-agent-manually.html). Workload monitoring is separately billed. Retained public IPv4 addresses cost [$0.005 per address-hour](https://aws.amazon.com/vpc/pricing/) (checked September 20, 2026).

Existing deployments with automatically created endpoints need a reviewed CloudFormation resource import or controlled handover before deploying this template; do not create a second private-DNS endpoint blindly. September 20 pre-rollout inspection found no endpoints/detectors in Stockholm or Cape Town, so both could use normal creation. Both now have one stack-owned endpoint, enable-only regional protection and HEALTHY automatic agents; both protocols pass and host/IP/task/parameter metadata is unchanged. [GuardDuty deployment flow](guardduty.md), [Stockholm evidence](launch-stockholm-ecs.md), [Cape Town evidence](launch-cape-town.md). Transport/IAM alone does not enable regional monitoring.

The disposable Northern Virginia exercise completed three cold deployments, both real protocol checks on each, and two subsequent normal teardowns without assistance, including a healthy-agent teardown. Rebuilds preserved credential/image identities while refreshing profile addresses; all test cloud resources and the temporary target were removed. Regional protection persisted. See the handoff for evidence.

Automatic agent v1.17.1 reached HEALTHY coverage; both real encrypted protocols and runtime security/memory checks passed. A repeated deployment changed nothing. Normal destroy removed all endpoint resources and released both EIPs without manual cleanup, preserving the exact regional feature/enrollment settings. Separate guarded test-only cleanup removed retained images/credentials and the temporary target; GuardDuty remains enabled. ## Optional expiration follow-up

No automatic expiry controller exists. A future lifetime policy could be permanent, idle timeout or fixed expiry, with stop/park/release as the chosen action. Select CLI versus phone-accessible launch before building a controller. Normal VPN packets cannot wake a deleted or stopped host.

Authenticated presence is not equivalent to interface state or EC2 network bytes. AWG keepalives and quiet/sleeping clients need explicit semantics; public scans must not extend a lease. Store aggregate activity and reporter health, not browsing destinations. A controller would need durable operation generations, serialized changes and explicit stale-telemetry handling. These are backlog decisions, not a second deployment architecture.

September 22 Bottlerocket replay: retained-IP park took about five minutes and restore about 6.6 minutes in Stockholm, excluding subsequent runtime/GuardDuty/client verification. These are observed samples, not timing guarantees. Explicit service-to-address dependencies keep management connectivity until the daemon stops; the final clean teardown passed the same ordering check. [Platform lifecycle](platform.md), [validation evidence](bottlerocket-trial.md).
