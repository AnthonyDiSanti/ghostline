# Shared gateway DNS

Ghostline's selected DNS design is one private CoreDNS container in the shared gateway task. Xray and AWG deliver ordinary client DNS to it through their existing tunnel adapters and the host's guarded port-53 interception. The resolver has no public listener, task role, protocol keys or engine configuration mounts. This is gateway-side DNS handling: it does not cause a device or browser to originate DoH, and applications that use their own encrypted DNS can bypass it.

CoreDNS listens on private UDP/TCP port 5353. It forwards to Cloudflare `1.1.1.1` and `1.0.0.1` first, then Google `8.8.8.8` and `8.8.4.4`, over certificate-checked DoT. The ordered policy falls back when a transport is unhealthy; it does not silently treat a normal upstream response as a reason to change providers. The host permits only these DNS-over-TLS destinations and blocks direct plaintext DNS egress from the gateway. Resolver DoT is SNATed to the host ENI's primary private IPv4, which currently has AWG's public EIP. It never passes through the AWG container. A later reassignment of the primary address changes DNS's public source without naming an engine in the DNS policy.

CoreDNS gives this shared layer room to add DoH or DoT listeners and DoH upstreams when client or network support warrants them. Those modes are not enabled now. We trust the selected upstream providers for validation and do not run an independent recursive DNSSEC validator. A future requirement for independent validation would reopen the CoreDNS/Unbound choice. [CoreDNS forward transport](https://coredns.io/plugins/forward/) and [server listener configuration](https://coredns.io/manual/configuration/) describe the available modes.

The retired Tor gateway experiment leaves no virtual-IP route, HTTP marker or Tor egress in the selected design. The special-use `.onion` zone returns local NXDOMAIN, so those names do not go to public upstreams. Browser access to onion sites remains outside this DNS release.

CoreDNS is an essential task member and must pass a real DNS health check before either engine starts. The static Go probe checks its local UDP/TCP listener, then resolves `example.com` or `google.com` to a public A record through the configured DoT forwarder. One working name suffices; three consecutive failed periodic checks mark the task unhealthy. This intentionally favors a replacement task during a sustained failure of both upstream providers, even though replacement cannot repair a provider-wide outage. Public names in the probe are fixed and never derived from client traffic. The local Docker package gate separately verifies listener behavior with networking disabled, requires full health to fail, and checks ordinary A/AAAA SERVFAIL through the same Go command. Go unit tests run in the builder stage; test code is absent from the runtime image.

ECS reports the task as `PENDING` while its engine containers wait on CoreDNS health. The host network daemon therefore recognizes the CoreDNS container in a pending task using the same ECS identity, restart generation and exact Docker UDP/TCP listener bindings used for running tasks. At that stage it permits only CoreDNS's four specified DoT destinations and primary-address SNAT. It admits engine egress only after ECS reports the task running. A missing or ambiguous binding keeps forwarding closed.

The first Stockholm rollout demonstrated the startup cycle in the prior daemon: local DNS passed, but upstream resolution could not run while ECS held the task pending, so the old daemon withheld DNS egress. Native ECS rolled that candidate back without moving production EIPs. The corrected daemon and real-resolution probe passed isolated Ireland qualification and Stockholm's second rollout; Stockholm now uses them. Cape Town has the same qualified release selected but remains parked.

The six-image release passed local and central native qualification in isolated Ireland. Its real A/AAAA/MX queries traversed both engine adapters and authenticated Cloudflare DoT; a bounded Cloudflare outage used Google DoT and restored the original firewall rules. Host-primary SNAT, normal HTTPS, cold start, blue-green EIP handoff and five-minute bake passed. The same selected release is published to all four enrolled registries. Stockholm passed native rollout, intercepted DNS and both encrypted client checks. Cape Town passed the same resolver and client checks after unpark, then returned to its parked backup state. [Regional evidence](launch-stockholm-ecs.md), [Cape Town evidence](launch-cape-town.md). A local image check or healthy ECS task alone does not prove client behavior. Device-side DNS control is described below.

## Device-side DNS boundary

The shared gateway DNS work is complete without device-originated DoH, and the owner accepts the resulting device boundary without further client-side DNS work for this project. Ordinary DNS sent through a working full-device tunnel is already encrypted on the local network by REALITY or AWG, then forwarded by CoreDNS over authenticated DoT. Both exported VPN endpoints use literal IP addresses, so connecting does not require a pre-tunnel hostname lookup. These observations do not prove that every app always uses the tunnel resolver; a browser can select its own encrypted DNS provider.

The AWG export specifies DNS server IP addresses, not a DoH endpoint. The exported REALITY/VLESS connection does not configure the device's system resolver. [Xray's built-in DNS](https://xtls.github.io/en/config/dns) supports DoH for queries it handles, but the client app must route system DNS into that component. OneXray's [published configuration contract](https://github.com/OneXray/OneXray/blob/main/docs/xray-configuration.md) exposes tunnel DNS IPs and an Apple DoT server name; its exact behavior in the installed build is not qualified here. Apple's [packet-tunnel settings](https://developer.apple.com/documentation/networkextension/netunnelnetworksettings/dnssettings) can supply DNS settings, and its [encrypted DNS APIs](https://developer.apple.com/documentation/networkextension/dns-settings) support DoH or DoT; a third-party client must implement and apply them. A separate Apple DNS configuration requires user enablement. [Chrome Secure DNS](https://support.google.com/chrome/answer/10468685) can choose its own provider independently of the VPN's resolver.

Future client-side DoH would therefore need a selected client/OS configuration, routing and leak tests on each device, and a policy for applications with their own DNS. DoH directly to a public provider could travel inside the VPN but bypass CoreDNS. DoH to Ghostline would require a reachable, certificate-validated listener and client support; the current CoreDNS listener is private UDP/TCP DNS only. Neither is required for this completed gateway DNS release.

## Logging and privacy gate

The current Corefile omits CoreDNS's `log` plugin, so normal successful queries are not deliberately logged. It does enable `errors`, which can print the queried name on a resolver failure. Stockholm's live ECS task sends the resolver's stdout/stderr to a local Docker `json-file` capped at 1 MiB. This is not a zero-traffic-log configuration. [CoreDNS query logging](https://coredns.io/plugins/log/), [error logging](https://coredns.io/plugins/errors/), [ECS log configuration](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task_definition_parameters_ec2.html).

The separate production privacy project is to inventory and eliminate Ghostline-retained client, destination and DNS-query records across the resolver, engines, host and diagnostics by default; qualify a separate explicit, short-lived deploy-time debug mode. It does not reopen the completed gateway DNS implementation. Verify the deployed task definition and actual host behavior, including failures, rather than inferring privacy from an absent CoreDNS query-log directive. GuardDuty and account audit are separate AWS security-data boundaries that need an explicit privacy decision before any absolute zero-log claim. [Product requirement](product.md#acceptance-and-privacy).
