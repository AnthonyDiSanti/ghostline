# Regional GuardDuty

Ghostline enables the GuardDuty protection available in the selected region. Confirmed service or capability gaps are acceptable and reported explicitly; they do not block a gateway deployment. Available protection stays enabled permanently. `infra/lib/guardduty.ts` accepts AWS defaults when creating a detector and only enables missing requirements on an existing detector. Regional settings have no Ghostline CloudFormation resource or teardown operation. The dedicated VPC endpoint, security group, host permissions and enrollment remain in [application IaC](deployment-lifecycle.md#guardduty-telemetry-lifecycle). Regional rollout evidence belongs in the launch records and handoff.

## Live availability and reduced protection

Every active CLI synthesis/deployment and monitoring check reads fresh AWS metadata through `infra/lib/guardduty-discovery.ts`. There are no cached regional flags, feature overrides or availability bypasses. Offline tests pass explicit synthetic discovery results into the shared app builder.

1. Query AWS's [public service-region catalog](https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-store-public-parameters-global-infrastructure.html) at `/aws/service/global-infrastructure/services/guardduty/regions`. The query runs in `eu-central-1`, our existing preflight region: AWS publishes this catalog only in selected query regions. The CLI paginates; incomplete/malformed results fail discovery.
2. If the selected region is absent, omit GuardDuty transport, installer permissions and host enrollment, make no GuardDuty API calls, and report `UNAVAILABLE`. The VPN stack still deploys normally.
3. If present, use regional EC2 endpoint-service discovery to check the Amazon-owned `guardduty-data` interface service in the selected AZ. When absent, omit transport/enrollment, enable foundational protection with AWS defaults and report `FOUNDATIONAL_ONLY` without waiting for agent coverage.
4. Read the detector's current feature list during reconciliation. A missing Runtime Monitoring feature or preserved legacy EKS-only protection also produces `FOUNDATIONAL_ONLY` with a reason. When runtime is supported and compatible, enable it and require the exact host's `HEALTHY` coverage.

API access failures, timeouts, malformed discovery, failed installation of supported protection and unavailable central discovery metadata remain errors; none proves regional unavailability. An apparent loss of transport support for an existing stack that already owns a GuardDuty endpoint also fails instead of removing installed protection. These safeguards do not prevent a cold deployment in a genuinely unsupported region. Later capability rollout is picked up on the next deployment.

September 20 discovery found GuardDuty in all 34 commercial regions listed by this account, consistent with [AWS service endpoints](https://docs.aws.amazon.com/general/latest/gr/guardduty.html). Taipei lacks RDS Protection according to [regional differences](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_regions.html), but supports EC2 Runtime Monitoring. Ghostline has no RDS workload: this gap does not reduce protection we use. [China has more restricted support](https://docs.amazonaws.cn/en_us/aws/latest/userguide/guardduty.html), including no Runtime Monitoring, but requires a separate partition/account; our commercial credentials cannot test it. Do not confuse AWS Config rule availability with GuardDuty feature availability. Full service absence and runtime absence are explicit simulated regression cases; the Taipei exercise tests acceptance of different regional defaults, not reduced protection for our workload.

## Creation defaults and enable-only updates

Anthony explicitly accepted AWS defaults on first creation on September 20. The service chooses regionally supported optional plans; Ghostline maintains no regional feature matrix, cached capability list or separate disabled-detector bootstrap. Every reconciliation reads current settings through [GetDetector](https://docs.aws.amazon.com/guardduty/latest/APIReference/API_GetDetector.html). Its region-dependent feature list is documented in the [feature API model](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty-feature-object-api-changes-march2023.html); the public API has no documented pre-creation capability query or dry run.

- Reuse the regional singleton without an ownership claim, configured ID, tag replacement or dependency on another project's templates.
- If missing, create with `Enable=true`; include only `RUNTIME_MONITORING=ENABLED` in `Features` when live telemetry discovery supports it. Omit optional plans and all `AdditionalConfiguration` overrides, accepting AWS's current defaults. New detectors carry the standard Project/Environment/System cost tags; these describe creation provenance, not exclusive management rights. If a runtime request is rejected and bounded rediscovery finds no concurrent creator, retry once using only AWS defaults. Accept this fallback only when the new detector explicitly reports a nonempty feature list without Runtime Monitoring; otherwise surface the original error. This handles a transport endpoint appearing before feature rollout without treating arbitrary failures as unsupported protection.
- For an existing detector, submit only missing `Enable=true` and/or supported, compatible `RUNTIME_MONITORING=ENABLED`. Never send disabled values, a stale full feature list, finding settings or tags in an update. Verify previously enabled features/agent settings remain enabled afterward.
- Recover a concurrent creator's BadRequest by bounded re-discovery and verification. Do not suppress authorization/transport failures; the narrow feature-absence fallback above also requires a verified detector. Verify enablement with up to ten two-second polling attempts; no rollback disables security on failure.
- An enabled legacy EKS-only Runtime Monitoring configuration requires a separately planned migration for EC2 runtime. Preserve it and continue with foundational protection. Organization policies/permissions can also prevent reconciliation; report failure rather than weakening protection.
- Stop, park and destroy leave regional monitoring enabled permanently. Removing the application also removes its host, agent and owned telemetry endpoint. Other regional workloads remain monitored according to their settings.

Ordinary reconciliation does not reset existing regions to new AWS defaults. Anthony separately authorized a one-time Stockholm/Cape Town alignment on September 20, using freshly created London's service response and each target's live feature list. That enabled S3 protection, EKS audit logs, EBS malware protection, RDS protection and Lambda protection in both existing regions. First creation in another region may enable additional billable protections or service-selected enrollment defaults.

Observed London defaults left `AI_PROTECTION`, `AI_ANALYST`, legacy `EKS_RUNTIME_MONITORING` and all Runtime Monitoring agent-management options disabled. These observations are acceptance evidence, not a policy table: the creation API chooses defaults, and subsequent deployment only enables missing project requirements. Tagged Ghostline hosts still enroll automatically. Do not infer that accepting defaults enables every available optional plan.

Its detector remains enabled after removing all test gateway/images/credentials; no temporary region stays in the deployment catalog. See [lifecycle evidence](deployment-lifecycle.md#guardduty-telemetry-lifecycle). The earlier Northern Virginia exercise reused existing protection and did not test this creation branch.

Sources: [detector scope/creation defaults](https://docs.aws.amazon.com/guardduty/latest/APIReference/API_CreateDetector.html), [targeted updates and EKS feature exclusion](https://docs.aws.amazon.com/guardduty/latest/APIReference/API_UpdateDetector.html).

`GetDetector` also reports foundational `CLOUD_TRAIL`, `DNS_LOGS` and `FLOW_LOGS` entries as enabled. These are expected alongside Runtime Monitoring, not optional plans accidentally activated. Do not copy the returned feature list into a create/update request; the request and response feature sets differ.

A detector still managed by another project's CloudFormation stack can be reused, but that owner's later update/deletion can conflict with the invariant. Do not silently remove or adopt its resource. ## Deployment and verification

Use `npm run ecs <target> deploy`. Read-only preflight checks launch inputs, parameter metadata, published images and live regional availability/settings. A fresh CDK diff precedes gateway deployment. Where runtime telemetry is available, gateway transport/host permissions are ready before `ensureGuardDuty` creates or enables regional monitoring, avoiding AWS creating transport outside the stack. Cold hosts depend on endpoint creation too.

Where runtime transport is supported, only the host receives `GuardDutyManaged=true`. With SSM connectivity and the scoped installer permissions, AWS installs and updates its agent automatically even when fleet-wide EC2 agent management is off. Never apply that tag to our IaC-owned endpoint/security group. [AWS enrollment behavior](https://docs.aws.amazon.com/guardduty/latest/ug/how-runtime-monitoring-works-ec2.html).

When Runtime Monitoring is available and compatible, deployment and read-only `ecs <target> verify` require the exact host's coverage to become `HEALTHY`. The gate polls up to 60 times at ten-second intervals and writes only detector/instance IDs, status, agent version or a reduced-protection reason to ignored `ecs/guardduty.json`. `FOUNDATIONAL_ONLY` and `UNAVAILABLE` are successful reduced-protection outcomes, never reported as healthy runtime coverage. A timeout neither disables monitoring nor tears down a working gateway. Resolve installation/telemetry failures and retry. A stopped or absent host is not expected to report live coverage; verify after starting/rebuilding.

No new notification destination is configured. Findings remain available in the regional GuardDuty console and existing AWS finding integrations. The enabler runs at deployment time; it is not a continuous drift controller. Local tests cover command contracts, preservation, races, failure handling, exact-host coverage and the absence of detector ownership from active/parked synths. They do not prove live installation or connectivity.

## Enrollment and broader protection policy

Anthony accepts AWS's optional-plan defaults for first creation and authorized the one-time alignment recorded above. For an existing detector, ordinary Ghostline deployment must **only enable missing deployment requirements and never disable existing settings**. Other plans are not additional preflight gates; further expansion remains separate account-security work.

Additional plans cover S3 access, EKS audit activity, RDS logins, Lambda networking, AWS AI-service activity and malware in EC2 disks, S3 objects and AWS Backup recovery points. Pricing is usage/resource/scan based; activation can immediately generate charges for existing workloads. See [feature overview](https://docs.aws.amazon.com/guardduty/latest/ug/what-is-guardduty.html) and [current pricing](https://aws.amazon.com/guardduty/pricing/). S3 malware protection needs [bucket plans and IAM](https://docs.aws.amazon.com/guardduty/latest/ug/enable-malware-protection-s3-bucket.html); backup scanning belongs in [AWS Backup workflows](https://docs.aws.amazon.com/guardduty/latest/ug/malware-protection-backup.html). Regional feature flags alone do not enable these everywhere.

[Extended Threat Detection](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty-extended-threat-detection.html) is automatically included without an additional charge. [Investigation/AI_ANALYST](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty-investigation.html) is a separate on-demand preview, available in Stockholm but not Cape Town; [AWS's announcement](https://aws.amazon.com/blogs/security/introducing-the-amazon-guardduty-investigation-agent-on-demand-ai-powered-threat-assessment/) states no preview charge, with 10 investigations/day and 100/account total. Investigation data may be processed across regions within its supported geography. AI Protection concerns Bedrock/AgentCore/SageMaker activity, not arbitrary external model APIs. Recheck preview pricing/availability before enabling it.

## Data and cost boundary

Foundational protection analyzes regional account activity using CloudTrail, EC2 flow and AWS Resolver DNS data; it is not confined to the gateway VPC. [Foundational sources](https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_data-sources.html).

The privileged AWS host agent sends process/container, file, network and DNS events to GuardDuty. DNS events can include queries/responses and connect events include remote addresses. This is security telemetry to AWS, not a promise of zero destination metadata collection. Keep secrets out of process arguments; GuardDuty can collect command-line arguments. [Collected events](https://docs.aws.amazon.com/guardduty/latest/ug/runtime-monitoring-collected-events.html).

The GuardDuty endpoint itself has no additional usage charge. Foundational analysis and runtime protection have usage pricing; persistent regional monitoring is not guaranteed to cost zero after host removal. No paid NAT gateway/load balancer is introduced. [Endpoint cost](https://docs.aws.amazon.com/guardduty/latest/ug/creating-vpc-endpoint-ec2-agent-manually.html), [GuardDuty pricing](https://aws.amazon.com/guardduty/pricing/).
