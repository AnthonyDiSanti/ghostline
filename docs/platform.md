# Bottlerocket platform

Every regional gateway uses AWS's official ECS-3 ARM64 Bottlerocket OS. The supported image includes the ECS agent and restricted SSM control container. Oregon, NVA, Stockholm and Zurich run official 1.66.0; Cape Town is parked. Launch records and the [handoff](../.context/handoff.md) own observed identities, validation limits and remaining upstream limitations.

## Images and ownership

The common pipeline builds, qualifies and publishes seven images: bootstrap, network-daemon, gateway-config, Xray, AWG, private CoreDNS policy and DERP/STUN. `GhostlineRelease` owns their local repositories plus non-runnable `releases` metadata. There is no independent helper cadence. CDK owns static local references/native settings; publication owns their targets and the whole-stack document. DERP's November 17 native qualification and running-fleet rollout are complete; the current seven-image proof is distinct from the earlier six-image proof. [Release workflow](releases.md), [DERP evidence](derp-poc.md).

The finite bootstrap image contains host preparation and explicitly invoked diagnostics. The separate daemon image excludes Docker CLI, mount tools, diagnostic fixtures and bootstrap-only dependencies. They share pure guard/network primitives in source, not authority or lifecycle. A successful `infra/platform-qualification.json` binds reusable native evidence to exact platform runtime manifests and build inputs; local image checks remain mandatory for each build. **Fresh native qualification must record the accepted startup availability limitation described below; prior failure evidence is never relabeled as a successful rollout.**

November 17 logging-remediation bytes passed central native qualification and all four active blue-green rollouts; [release evidence](../.context/scratch/2026-11-17-zero-logs-release/README.md). The accepted upstream startup limitation remains; this is not an OS repair.

## OS policy

Select the latest official stable ECS-3 ARM64 version centrally, qualify it, and record `os.targetVersion` in the whole-stack release document. New hosts use `resolve:ssm:/aws/service/bottlerocket/aws-ecs-3/arm64/<targetVersion>/image_id`. EC2 resolves that version's regional AMI at launch; it does not independently choose a newer unqualified OS. Preflight verifies Amazon ownership, ARM64, available state and the exact image name/version. The global document contains no regional AMI ID.

Every meaningful app, daemon, bootstrap, qualified OS or host-template change prepares a temporary green host, then uses the same [native ECS rollout and EIP handoff](releases.md#regional-state-machine). The host OS remains an AWS AMI, not an OCI image. An ordinary reboot retains that host's OS. The in-place TUF update command is retired; a newly qualified OS is delivered by green-host replacement. Scheduled cloud builds remain separate future work.

```sh
npm run platform stockholm-ecs status
npm run platform <qualification-target> qualify /absolute/path/to/qualified.json
```

`qualify` records actual runtime/OS evidence only after the disposable native experiment and live security checks. Local package tests alone cannot qualify a new host/platform path.
DNS-enabled qualification requires the exact six-image local build record, including the DNS image. Ireland passed selected ECS service generation, manual-mode blue-green handoff and native failed-green rollback with explicit cleanup. The October 26 source bytes also passed central platform qualification; this does not prove client-side DoH or ordinary-browser `.onion` access.

## Recovery and evidence limits

Unexpected native boot does not fetch a release document or wait for a perfect version match. Essential swap/capacity/private-RAM/quarantine checks still apply. Bootstrap records its successful digest, OS and current boot ID through a constrained nonsecret native API operation; observation failure does not block otherwise safe boot. The fixed read-only observer checks the current kernel boot ID and native settings, since ECS registration attributes can remain stale after reboot.

**Bottlerocket 1.65 and 1.66 did not fall back to a cached bootstrap image after an ECR 403.** Bounded Ireland fault tests verified the cached alias before denying only that host’s bootstrap-repository pulls, then observed essential bootstrap failure before ECS. Removing the test deny and explicitly rebooting restored the same host/endpoints on both versions. The 1.66 test also restored administrative lockdown before completion. Release-metadata tolerance is not an offline-image guarantee. Retain required artifacts and local copies, but do not make bootstrap optional or bypass verification for availability.

Ireland also passed signed TUF preparation, reboot before activation, cancellation, boot into 1.64.0 and normal-wave return to 1.65.0. The updater lock hid exact write progress, so this is not proof of a precise mid-write interruption. [Native updater](https://bottlerocket.dev/en/os/1.64.x/update/methods/in-place/), [bootstrap settings](https://bottlerocket.dev/en/os/1.64.x/api/settings/bootstrap-containers/); exact-version claims above come from live evidence, not older documentation alone.

The subsequent deployed-controller experiment passed application-only, daemon-only and combined changes, but one bootstrap-only transition failed in native host-containerd before our entrypoint ran: a parent filesystem snapshot was missing after successful pull/unpack. The controller issued one reboot, timed out and paused without retrying. One explicit diagnostic reboot recovered the same host; this is recovery evidence, not successful unattended rollout. A later controlled test reproduced the missing-parent failure with the selected client and server, then with Ireland's actual native overlayfs snapshotter. The standard containerd pull-and-unpack path survived the same forced GC. This is strong evidence for an upstream client-path defect, although the original boot's exact GC timing was not captured. The [supported-pattern audit](../.context/scratch/2026-09-22-coordinated-release/bootstrap-pattern-audit.md) found no invalid bootstrap setting explaining the failure; [core-kit issue #1059](https://github.com/bottlerocket-os/bottlerocket-core-kit/issues/1059) reports the bounded evidence. Native `host-ctr` is OS software, so a Ghostline bootstrap image cannot repair it. Anthony accepted this startup availability limitation while pursuing [PR #1063](https://github.com/bottlerocket-os/bottlerocket-core-kit/pull/1063). Fresh exact-image/1.66 qualification, including the then-current bounded recovery behavior, preceded the September 26 production migration. An official repair must still pass native replay/recovery checks before its limitation is removed. See the [investigation and candidate source patch](../.context/scratch/2026-09-22-coordinated-release/native-bootstrap-failure.md).

## Startup failure policy

The former in-place controller's one-extra-reboot exception is retired with that controller. This does **not** mean core-kit #1059 is fixed. A failed green boot is retained for diagnosis; it never starts an autonomous reboot loop. Blue remains available until green passes readiness. Continue checking #1059/PR #1063 at major milestones and qualify the official repair before removing the documented limitation.

## Boot and runtime boundaries

There are two different preparation containers: Bottlerocket's **host bootstrap creates the RAM filesystem**; the later **ECS initializer fills it with configuration**. Bootstrap is not an ECS task and does not need the ECS agent or Docker to be running.

1. EC2 boots the official OS. The launch template supplies Bottlerocket settings through user data, including the bootstrap image and `mode=always`, `essential=true`. User data contains public topology/settings, not application secret values.
2. Bottlerocket/systemd starts its separate `host-containerd` runtime. Its native bootstrap launcher configures `bootstrap-containers@ghostline.service`; `host-ctr` pulls/starts the bootstrap image. This is OS orchestration, not ECS scheduling, and uses host infrastructure permissions for image access.
3. Our finite [bootstrap](../runtime/ecs/bottlerocket/bootstrap.py) invokes [storage preparation](../runtime/ecs/bottlerocket/storage.py). It checks swap/capacity, mounts a protected tmpfs with a **2 MiB limit** at host `/mnt/ghostline/config`, and creates its private `xray`/`awg` and configured `derp` subdirectories. It then installs the empty forwarding guard and attempts to record nonsecret boot identity. No server secrets are read in bootstrap. The existing native tmpfs label is retained; preparation does not relabel the filesystem.
4. Bootstrap exits successfully; systemd can complete `configured.target`. An essential bootstrap failure blocks later workload startup. `mode=always` repeats this finite phase on every boot, including reboot/stop-start; it is not a continuously running helper.
5. The workload container runtime/Docker start, then the ECS agent starts and registers the host. ECS schedules the network DAEMON task and gateway task. Their relative process-start order alone is not the forwarding safety guarantee: the preinstalled guard stays closed until the daemon supplies valid routing/leases.
6. ECS creates `gateway-config` with public parameter references and a task credential locator. After private DNS is healthy and the network daemon grants its verified short-lived lease, the initializer uses the **task role** to retrieve Xray/AWG/DERP server values directly into memory, renders through private pipes into the **already mounted** RAM directory and exits. Neither the host nor execution role reads application parameters in this recipe. Read launch records for whether a host has adopted it.
7. Engines require initializer `SUCCESS` and private DNS `HEALTHY`, then read only their own protocol RAM directory. The network daemon must maintain the forwarding lease for traffic to pass. ECS also creates separate per-container `/run` and `/tmp` tmpfs scratch mounts where declared; these are distinct from the shared credential-config mount created in step 3.

The official [1.66.0 release manifest](https://github.com/bottlerocket-os/bottlerocket/blob/v1.66.0/Twoliter.toml) selects Core Kit 17.0.0. Its [bootstrap unit](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/v17.0.0/packages/os/bootstrap-containers%40.service) runs before `configured.target`; the [native launcher](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/v17.0.0/sources/api/bootstrap-containers/src/main.rs) makes an essential bootstrap required by that target. [Docker](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/v17.0.0/packages/docker-engine-29/docker.service) runs after it, and the [ECS agent](https://github.com/bottlerocket-os/bottlerocket-core-kit/blob/v17.0.0/packages/ecs-agent/ecs.service) runs after Docker. This confirms the source dependency order; it does not qualify a proposed new runtime-storage mount or prove every runtime persistence path is RAM-only.

The 2 MiB tmpfs does **not** include Docker metadata, images or ECS checkpoints. The former ECS-injected secret environment persisted in both Docker and the ECS checkpoint on EBS. The supported bootstrap storage mounts do not cover checkpoint data; the selected fix avoids injecting plaintext into either runtime's creation model. [Native storage evidence and delivery decision](../.context/scratch/2026-11-17-zero-logs-release/credential-delivery-plan.md).

The network daemon's only added capabilities are NET_ADMIN and NET_RAW; it has no host filesystem mounts, Docker socket, host PID access, devices, task IAM or secrets. Root is read-only, privilege escalation is disabled, seccomp applies and ordinary container SELinux policy enforces.

The daemon continuously validates ECS introspection identities against kernel Docker port bindings. It maintains routing, protocol/EIP separation and five-second kernel forwarding leases. Ambiguous discovery, stalled or dead controllers close forwarding. ECS health checks replace a failed daemon. NET_RAW is required by the actual iptables IP-set matcher; a successful standalone ipset creation does not prove that NET_ADMIN alone suffices.

Bottlerocket's read-only verified OS and enforcing SELinux remain enabled. The admin container is disabled and ECS privileged containers are disallowed. Both slot launch templates opt out of AWS's privileged GuardDuty Runtime Monitoring host agent. The ephemeral bootstrap and explicitly enabled diagnostic container have broader host access; the steady-state Ghostline daemon does not.

## Diagnostics and lifecycle

`ecs <target> verify` briefly enables the maintained diagnostic host container, verifies native ARM64, config hashes, private read-only tmpfs, engine/daemon confinement, cgroups and network isolation, then disables diagnostics and reads back the disabled admin/diagnostic state. Cleanup runs even when startup or verification fails. Credential comparisons and the Runtime Monitoring exclusion check happen after lockdown. Secret values never enter terminal output or agent context.

The lifecycle controller retains EIP connectivity until gateway and daemon tasks actually stop and the retiring host is terminated; it then detaches addresses and removes that slot’s ENI. This preserves the host agent’s internet connection while it acknowledges the final task stop; removing the IPs first can leave an empty-looking service stuck draining.

Stop scales down the gateway, drains every owned overlapping host, waits for its daemon to stop and then stops EC2. Start waits for host/agent health, reactivates placement, waits for a healthy daemon and starts a new gateway task. Park deletes both disks, compute and VPC resources, retaining the two tracked EIPs; unpark rebuilds using the same image selection and Parameter Store identities. See [lifecycle](deployment-lifecycle.md) and [central qualification](bottlerocket-trial.md).
