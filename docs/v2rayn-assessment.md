# v2rayN Mac client assessment

Reviewed 2026-09-13 at Anthony's request before client selection. **v2rayN is a credible open-source route to one Mac app for both protocols, but it needs separate Xray and Mihomo engines for our unchanged servers.** Codex still recommends OneXray first for the immediate REALITY-only sleep/crash experiment; v2rayN becomes more attractive if replacing AWG's client is also a priority. This is a recommendation, not owner selection or local validation. [Incident evidence and current client scope](mac-client-stability.md).

## Maintenance and distribution

The [project](https://github.com/2dust/v2rayN) publishes GPL-3.0 application source and Windows, Linux and macOS builds. GitHub reports about 116k stars; that establishes broad project interest, not Mac user counts or sleep reliability. Current [7.24.9](https://github.com/2dust/v2rayN/releases/tag/7.24.9), published August 29, is marked stable by the live release API; older search snapshots call it a prerelease. The desktop uses Avalonia/.NET. Official arm64 DMG/ZIP assets exist, with GitHub SHA-256 metadata and detached GPG signatures.

Release notes describe an urgent fix for an older downloader vulnerability permitting MITM and malicious downloads. Use the current fixed release, not an older build to avoid UI changes. The reviewed [downloader](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Helper/DownloaderHelper.cs) uses TLS certificate validation; this is not an independent security audit. Release signatures are published, but verification of those signatures was not found in the inspected in-app update path. GitHub metadata hashes are not independent provenance.

The [Mac packaging script](https://github.com/2dust/v2rayN/blob/7.24.9/package-osx.sh) merges a core archive from the project's separate core-bin repository at its mutable master branch. Therefore an app tag alone does not pin the bundled engine versions. Confirm the actual binaries before trial. The reviewed packaging/signing workflow establishes GPG release signing, not Apple Developer ID notarization. No official main Homebrew cask was found; the checked cask path returned 404. Use official release provenance if selected; installation and any Gatekeeper prompt remain untested.

## Protocol and tunnel design

| Workload | Viable v2rayN configuration | Evidence and limit |
| --- | --- | --- |
| Stockholm VLESS/REALITY | Current Xray engine with existing credentials | Xray 26.7.28 already passed our separate control test. The v2rayN frontend and its generated full-device routing remain untested. |
| Stockholm AWG 3.1 | Mihomo 1.19.30 with a local custom YAML profile | [Release](https://github.com/MetaCubeX/mihomo/releases/tag/v1.19.30) ships AWG 3.0/3.1; [implementation](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/adapter/outbound/wireguard.go) includes v3.1 fields. Exact credential/obfuscation translation and connectivity remain untested. |
| Both through Mihomo alone | Incompatible with the preserved REALITY policy by source analysis | [Mihomo 1.19.30](https://github.com/MetaCubeX/mihomo/blob/v1.19.30/component/tls/reality.go) writes client-version bytes `1.8.2`, below our Xray server's observed `26.3.27` floor. No live Mihomo failure was claimed or server policy changed. |

v2rayN's [core manager](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Manager/CoreManager.cs) launches ordinary privileged engine processes for Mac TUN. This is not an Apple Packet Tunnel app/system extension. System-proxy mode alone covers applications that honor proxy settings; our full-device objective requires TUN and validation of DNS/IPv6 routing.

The [default legacy-protection option](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Handler/ConfigHandler.cs) uses sing-box as a local TUN-to-SOCKS frontend for an ordinary Xray profile. **That does not recreate SFM's REALITY authentication failure:** Xray still performs the remote handshake. Disabling that option selects Xray TUN instead. Custom Mihomo configurations can use Mihomo's own TUN; no extra SOCKS frontend is needed when its pre-SOCKS port is unset. The [embedded Mihomo TUN template](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Sample/clash_tun_yaml) uses gVisor, automatic routes/interface detection and port-53 DNS interception.

Custom YAML is not used verbatim: [CoreConfigClashService](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Services/CoreConfig/CoreConfigClashService.cs) rewrites local ports, logging, IPv6, controller, LAN access and, when enabled, TUN. It preserves the nested proxy dictionaries used for AWG, but inspect the generated output before claiming an exact import. DNS AAAA suppression alone is not proof that literal IPv6 traffic cannot bypass the tunnel.

## Client control and privileges

- **No Happ-like provider push channel identified** in the scoped source/dependency review. Local profiles need no provider account. Configured subscriptions are pulled; they can change their supplied configuration when refreshed. Standard GitHub release checks, selected rule downloads and connectivity tests are still network activity. Searches found no obvious telemetry SDK/device-registration channel; they do not certify the binary or every dependency.
- **The app handles the sudo password itself.** Its [password dialog](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/v2rayN.Desktop/Views/SudoPasswordInputView.axaml.cs) verifies it with `sudo -S`; the [status view](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/v2rayN.Desktop/Views/StatusBarView.axaml.cs) stores it in `AppManager.LinuxSudoPwd`. [CoreAdminManager](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Manager/CoreAdminManager.cs) reuses it over stdin to start/stop privileged engines. No persistence of that field to configuration was found, but it is a managed string retained in process memory, not an OS-owned authorization prompt or zeroized secret buffer. This is a material trust tradeoff, not evidence of exfiltration.
- **Mihomo exposes a local control API.** The config adapter sets `external-controller` to `127.0.0.1` and explicitly removes `secret`; the GUI uses it to select proxies, inspect connections and reload configuration. This is a local unauthenticated control surface, not a vendor-operated remote channel. Other local processes can reach it; loopback is not an authentication boundary. Mixins/custom settings can change the final configuration, so verify the actual listener and leave LAN sharing off if trialing it. Do not promise a token can simply be added without checking GUI compatibility.
- **Optional remote features require care, but are unnecessary here.** [Subscription conversion](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Handler/SubscriptionHandler.cs) sends the subscription URL to a configured/default conversion service only when a conversion target is selected. Avoid that feature for private Ghostline profiles. [WebDAV](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Manager/WebDavManager.cs) is owner-configured backup/restore, not mandatory provider administration. [Scheduled tasks](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Manager/TaskManager.cs) check releases roughly daily and pull subscriptions only with a positive configured interval; checking releases is distinct from silently installing them.

## Stability evidence

The issue search found relevant Mac maintenance activity, not proof of the same failure or its absence:

- [#9765](https://github.com/2dust/v2rayN/issues/9765): maintainer-confirmed Xray TUN geodata-path startup failure affecting macOS/Linux around 7.23.4. Closed now; closure alone does not establish a current-device pass.
- [#9863](https://github.com/2dust/v2rayN/issues/9863), including duplicate [#9842](https://github.com/2dust/v2rayN/issues/9842): Mac TUN stop/restart leaves ports occupied or internet unavailable. Maintainer added shutdown delay and requested 7.24.5 testing; one commenter reports success. This shows a concrete mitigation and user confirmation, not universal resolution or a current 7.24.9 failure.
- [#9973](https://github.com/2dust/v2rayN/issues/9973): open Intel Mac 7.24.7 drag-sort app crash, a different platform/trigger from our Apple Silicon sleep panic. [#8187](https://github.com/2dust/v2rayN/issues/8187) reports high local-request load/heat after sleep or network loss on macOS 14.8; closed as not planned, exact cause/current reproducibility unverified.

No matching v2rayN configd-watchdog/kernel-lock report was identified in the English/Chinese searches. Do not infer immunity or rank clients by raw issue counts. A separate [Tailscale macsys report](https://github.com/tailscale/tailscale/issues/20359) describes a similar configd/network-lock stall involving an Apple NetworkExtension. It does not prove the same defect here, but reinforces that Apple's extension architecture alone cannot guarantee sleep safety.

## Recommendation and next evidence

For the currently selected REALITY-only replacement, **try OneXray first and retain Streisand as the next simple alternative**. v2rayN's open source, mature ecosystem and AWG-capable engine make it a credible alternative for consolidating both protocols; its privilege handling, local API and engine/configuration coordination add tradeoffs for this short stopgap. No provider-control mismatch comparable to Happ was established. Do not disqualify it merely for using desktop TUN, or claim OneXray is proven more stable.

If selected, use the fixed official arm64 release, verify Xray/Mihomo versions, import existing identities as local profiles and inspect generated routing/DNS/listeners. Test awake connection and disconnect/reconnect per protocol, then owner-coordinated repeated sleep/wake with new-report inspection. Keep server settings and iPhone/Cape Town unchanged. No custom client patch, blanket macOS security relaxation or server floor reduction is part of the proposal.

Read-only evidence lives under ignored `.local/research/v2rayn-2026-09-13/`: release/repository metadata, source-archive hash, selected text sources, pinned Mihomo implementations and issue comments. Downloaded source scripts were not executed. No app/binary installation, credential access/import, native network change or cloud mutation occurred. Remaining uncertainties require a trial rather than another general search.
